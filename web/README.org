#+subtitle: the same formatter and the same rules, compiled to WebAssembly
#+author: Josep Bigorra

* What this is

sift is a formatter, a linter and a language server.  Two of those three are a
function of a string: give the formatter a buffer and it answers another buffer;
give the linter a buffer and it answers findings.  This directory is that
function, compiled to WebAssembly with [[https://spritely.institute/hoot/][Guile Hoot]], and an editor page
around it.  The buffer never leaves the tab: there is no server, no request, and
nothing to trust with your code.

#+begin_quote
It is the same Scheme that ~bin/sift~ runs.  Not a reimplementation, not a
subset: the reader, the formatter and all 93 rules are the modules in
~src/sift/~, and all this directory adds to them is the facade that turns a JSON
request into a call.  The dependency runs one way -- ~web/~ imports the core,
and the core has never heard of ~web/~ -- and three tests hold that direction.
#+end_quote

* Building it

One command, from the root of the checkout:

#+begin_src shell
./web/build.sh            # writes web/dist/
./web/build.sh /tmp/out   # or wherever
#+end_src

It finds a Hoot that works, or asks Guix for one, or says what is missing.  The
first build on a machine takes a while, because ~guix shell guile-next
guile-hoot~ may have to fetch those two; every build after it is seconds.
~maak web~ is the same command, run through the task runner.

Hoot is the compiler, and it is needed once, at build time; nothing it produces
needs it at run time.  The Wasm module wants a browser with the GC and
exception-handling proposals -- Firefox 121+, Chrome 119+, Safari 26+ -- and the
build itself wants ~guild~.

Finding Hoot is the only hard part of that script, and it is hard in one specific
way worth writing down, because the failure is not the one you would guess.
Hoot's compiled modules are bytecode, and bytecode belongs to the Guile that
compiled it: ~guix shell guile guile-hoot~ puts Guile 3.0.9 beside a Hoot built
for Guile 3.0.10, and what comes out is not "Hoot is missing" but ~Unbound
variable: default-debug-level~, from inside Hoot, half way through a compile.  So
the script does not look for ~guild~ and hope.  It compiles a two-line program,
which is a question only a working toolchain answers, and when the answer is no
it asks Guix for ~guile-next guile-hoot~ -- the pair ~guile-hoot~ is built
against -- and builds there.

That writes ~web/dist/~, which is a directory a static file server can serve:

#+begin_src shell
maak web-serve                                # http://localhost:8080/
cd web/dist && python3 -m http.server 8080    # the same thing by hand
#+end_src

It has to be *served*, not opened from the file system: a ~file://~ page may not
fetch the ~.wasm~ it needs, and the reflection runtime fetches its own helpers.
~maak web-serve~ is that and nothing more -- Python's static file server, which
every machine has -- and no part of publishing uses it.

| File            | What it is                                                             |
|-----------------+------------------------------------------------------------------------|
| ~index.html~    | the page, with the build stamp written into every URL it names          |
| ~editor.js~     | the editor: one request per keystroke, debounced                        |
| ~editor.css~    | the look, and the two rules that keep the highlight layer aligned       |
| ~favicon.png~   | the project's own icon, so a served page is a page with no 404 in a log  |
| ~sift.wasm~     | sift, compiled                                                          |
| ~reflect.js~    | Hoot's JavaScript half of the reflection runtime                        |
| ~reflect.wasm~  | and its Scheme half, beside the module that loads it                    |
| ~wtf8.wasm~     | the string encoding helper the two use                                  |

The stamp is the version, the commit and the minute the build ran --
~1.15.0-9f55646-20251102T144123Z~ -- and it is in the page's URLs because the
server offers these files with a long ~Cache-Control~.  A URL that does not
change is a deploy nobody sees: the browser keeps the module it has.  ~editor.js~
reads the same stamp out of its own URL and puts it on ~sift.wasm~, and it finds
both beside itself rather than at the root of a site, because the directory it is
served from may be ~https://jointhefreeworld.org/sift/~ and not ~/~.  Both are
asserted in ~tests/web.scm~, and both are what make the page work in a
subdirectory at all.

** Pointing the script at a different Guile

The script uses ~guile~ and ~guild~ from ~PATH~ when they can compile, and asks
Guix when they cannot.  A machine with its own Hoot -- from Nix, or built from
source -- names it instead, and is trusted as named:

#+begin_src shell
SIFT_HOOT_GUILE=/gnu/store/...-guile-next/bin/guile \
SIFT_HOOT_GUILD=/gnu/store/...-guile-next/bin/guild \
  ./web/build.sh
#+end_src

| Variable           | What it does                                                     |
|--------------------+------------------------------------------------------------------|
| ~SIFT_HOOT_GUILE~  | the Guile to compile with, instead of the one on ~PATH~           |
| ~SIFT_HOOT_GUILD~  | the ~guild~ beside it                                             |
| ~SIFT_HOOT_SHELL~  | the Guix packages to ask for, instead of ~guile-next guile-hoot~  |


* Publishing it

It is served from the same machine and the same certificate as the rest of
jointhefreeworld.org, so publishing it is a copy:

#+begin_src shell
maak web-deploy
#+end_src

That builds the page and puts it at ~/srv/http/jointhefreeworld.org/sift~, which
is what nginx serves as https://jointhefreeworld.org/sift/.  The directory is
emptied first, so a file this build does not have does not linger beside the file
that replaced it, and the build directory is removed afterwards the way
~maak deploy~ in Maak's own file removes the documentation it publishes.

It runs where that directory is: on the machine that serves, or in the CI job
that runs there.  There is no ssh in it, no rsync, and no server to reload,
because a file that is there is a file that is served.

Nothing about the server had to be arranged for it either.
jointhefreeworld.org already serves ~/srv/http/<name>~ as ~https://<name>/~ with
a certificate over HTTP/2 and HTTP/3, so a directory that is there is a page that
is up.  Three things the page depends on and does not configure: nginx maps
~.wasm~ to ~application/wasm~ (a module it types as anything else is one the
browser refuses to instantiate), it redirects a directory requested without its
trailing slash (without which every relative URL in the page resolves one level
too high), and it compresses the module.  The one behaviour it has to be worked
*with* is the cache -- ~Cache-Control: public, max-age=172800~ on ~.wasm~,
~.js~ and ~.css~ -- which is what the build stamp is for.

* What it can do

| In the page                          | What answers it                              |
|--------------------------------------+----------------------------------------------|
| lint as you type                     | every rule the dialect applies to            |
| ~Format~, or ~Ctrl-Shift-F~          | the formatter, with the style and the dialect |
| ~Fix~, or ~Ctrl-Shift-X~             | the same all-or-nothing fix run ~sift fix~ does |
| ~Ctrl-Shift-E~, ~Ctrl-Shift-R~       | extract the expression at the caret to a ~let~, or to a procedure |
| the findings panel                   | rule, code (~SIFT012~), severity, place      |
| click a finding                      | the cursor goes to it                        |
| the context bar                      | a hover: what the symbol under the caret is  |
| ~Ctrl-Space~                         | completion of the names the buffer defines   |
| ~F12~ or ~Ctrl~+click                | jump to the definition, in this buffer       |
| ~Outline~                            | the buffer's definitions, click to go there  |
| ~Rules~                              | every rule, with its example                 |
| the dialect selector                 | Scheme, Emacs Lisp or Common Lisp            |

The four editor questions -- hover, definition, completion, outline -- are
answered by *the language server's own code*, not by a second implementation:
~sift lsp~ splits into ~(sift analysis)~, which answers about a buffer and a
workspace, and the rest, which reads a project off a disk and speaks JSON-RPC.
The browser compiles the first and asks it with an empty workspace, so a
definition inside the buffer is found, a definition in a file the tab has never
seen is not, and nothing pretends otherwise.

What it cannot do is anything that is about a *project*: there is no directory
to walk, no ~sift.yaml~ to read, no file to save, and no language server.  Two
rules are affected and both say so honestly rather than guessing:

- ~library-not-found~ (SIFT060) asks the project which libraries it declares.
  A tab has no project, so the rule never fires.
- ~unused-import~ (SIFT061) knows what the project declares in ~src/~ or
  wherever the libraries live.  In a tab it knows only what the buffer itself
  declares.

Neither invents an answer, which is the point: a rule that cannot see the
project says nothing, and the editor shows the ninety that can.

* How it works

The whole contract between the editor and the Scheme is one procedure of one
string to one string.  ~web/main.scm~ is the entry point and its last
expression is that procedure:

#+begin_src scheme
(import (scheme base)
  ;; sift:disable-next-line library-not-found
  (sift web))

(values web-request)
#+end_src

so the JavaScript side is four lines, and the fourth is the point of the other
three: the module, and the wasm beside it, are wherever this module was loaded
from, and the stamp the page put on this module's URL goes on the wasm too.

#+begin_src javascript
const moduleUrl = new URL(import.meta.url);
const wasmUrl = new URL("sift.wasm" + moduleUrl.search, moduleUrl).href;
const reflectDir = new URL(".", moduleUrl).href.replace(/\/$/, "");
const [sift] = await Scheme.load_main(wasmUrl, { reflect_wasm_dir: reflectDir });
const answer = JSON.parse(text(sift.call(JSON.stringify(request))[0]));
#+end_src

(~text~ is there because a Scheme string is mutable, and Hoot hands mutable
strings over as objects; ~reflector.string_value~ is how the page reads one.)

** The seam

The directory is laid out so that the dependency runs one way:

#+begin_src text
src/sift/            the core: the library bin/sift installs
  reader.scm  format.scm  lint.scm  json.scm  records.scm  ...
web/
  sift/web.scm       the facade: JSON in, JSON out
  main.scm           the Wasm entry point: (values web-request)
  compat/            stand-ins for the Guile libraries the target has not
  index.html  editor.js  editor.css  build.sh
#+end_src

~web/sift/web.scm~ is a module under its own load-path root, which is why the
build passes ~-L web~ beside ~-L src~: Scheme resolves ~(sift web)~ to a path
under a load path, and the facade is deliberately not part of what ~bin/sift~
installs.  It is ordinary portable Scheme -- it imports the same ~(sift
format)~, ~(sift lint)~, ~(sift json)~ and ~(sift records)~ that the command line
does and calls the same entry points -- which is what lets ~tests/web.scm~ drive
the browser build's whole surface under Guile, in the same process, without a
browser: what the tests assert is what the tab runs.

Nothing in ~src/sift/~ mentions the browser, ~web/sift/web.scm~ imports four core
modules and no more, and every Guile library the browser build reaches has
either a stand-in in ~web/compat~ or a note saying the target ships it.  All
three are asserted in ~tests/web.scm~:

#+begin_src scheme
(test "the core does not know the browser exists" ...)      ; no `hoot', `wasm',
                                                            ; `browser' in src/sift/
(test "the facade imports four core modules, and no more" ...)
(test "every Guile library the browser build imports has a stand-in" ...)
#+end_src

so the seam is a test rather than a habit, and each test answers a different
question.  Add an import to the core and the third one names it -- before a Wasm
build gets the chance to.  Teach the facade a new core module and the second one
says the browser's dependency just grew.  Start explaining the core in terms of
a tab and the first one fails with the file's name.

** The protocol

A request is a JSON object with an ~op~, and every answer is
~{"ok":true,"result":...}~ or ~{"ok":false,"error":{"kind":...,"message":...}}~.
The kinds are ~request~ (the document is not JSON), ~usage~ (a member is the
wrong type or names something sift does not have) and ~internal~ (a bug in sift,
which a tab reports rather than dies of).

| ~op~        | Answers                                                              |
|-------------+----------------------------------------------------------------------|
| ~format~    | ~{"source":S',"changed":B,"warnings":W}~ -- the text, and the reader's own findings |
| ~check~     | the same, which is exactly the question ~sift check~ asks             |
| ~lint~      | ~{"warnings":W,"counts":C,"severity":A}~                               |
| ~fix~       | ~{"source":S'',"applied":N,"changed":B,"warnings":W}~                  |
| ~extract~   | ~{"source":S',"title":T,"changed":B}~ -- the expression at ~offset~, bound |
| ~checkers~  | ~{"version":V,"checkers":K}~ -- the rule catalogue, with examples      |
| ~version~   | ~{"version":V}~                                                       |
| ~hover~     | ~{"hover":{contents,range}}~ or ~null~ -- what the symbol is           |
| ~definition~| ~{"definitions":[{uri,range}]}~ -- in this buffer only                 |
| ~references~| ~{"references":[{uri,range}]}~ -- in this buffer only                  |
| ~highlight~ | ~{"highlights":[{range,kind}]}~ -- declaration apart from use          |
| ~symbols~   | ~{"symbols":[DocumentSymbol]}~ -- the outline, nested                   |
| ~completion~| ~{"items":[{label,kind,sortText}]}~                                    |
| ~signature~ | ~{"signature":SignatureHelp}~ or ~null~                                |
| ~inlayHints~| ~{"hints":[{position,label,kind}]}~ -- parameter names beside arguments |

The last eight take the buffer, the dialect and an ~offset~ (a character index
in the buffer; ~inlayHints~ takes ~from~ and ~to~ instead, defaulting to the
whole buffer), and answer in the language server's shapes: a range is a line
and a character, both zero based.  They are the same procedures ~sift lsp~
answers with.  Completion and inlay hints are offered in the page; signature
help is in the context bar when the caret is inside a call.

and the members a request may carry:

| Member             | Applies to        | What it is                                         |
|--------------------+-------------------+----------------------------------------------------|
| ~source~           | all but ~checkers~| the buffer, as a string                            |
| ~dialect~          | format, lint, fix | ~scheme~, ~elisp~ or ~cl~ (default ~scheme~)        |
| ~style~            | format            | ~community~ or ~dangling~                          |
| ~indent~           | format, lint      | indentation width, in columns                      |
| ~brackets~         | format            | ~square~, ~parens~ or ~preserve~                    |
| ~blankLines~       | format            | ~preserve~ or ~one~                                |
| ~commentAlign~     | format            | line up contiguous inline comments                  |
| ~indentRules~      | format            | ~[["with-my-thing", 2], ...]~ for a project's macros |
| ~severity~         | lint, fix         | the smallest severity to report (default ~info~)   |
| ~checkers~         | lint              | run only these rules                               |
| ~excludeCheckers~  | lint              | skip these rules                                   |
| ~label~            | lint, fix         | the name findings carry, instead of nothing        |
| ~lineLength~       | lint              | the soft line limit                                |
| ~options~          | lint              | any other checker setting, by its ~sift.yaml~ name |

A finding is ~{"rule","code","severity","message","line","column","offset","from","to","fixable"}~;
~from~ and ~to~ are character offsets, which is what an editor underlines.

* The compatibility layer

Hoot is not Guile: it compiles R7RS and a subset of Guile, and the difference is
what ~web/compat/~ exists for.  It sits at the *front* of the module load path
when building for the browser (see ~build.sh~), so an `(ice-9 ...)' or
`(srfi ...)' import in sift's sources finds it, and not one line of
~src/sift/~ had to be rewritten for a platform without Guile.

| Shim                                  | Why                                                                |
|---------------------------------------+---------------------------------------------------------------------|
| ~compat/ice-9/format.scm~             | Hoot has no ~format~; this is ~a ~s ~d ~x ~o ~b ~f ~c ~% ~& ~~ with the numeric parameters sift uses |
| ~compat/ice-9/textual-ports.scm~      | ~get-string-all~, ~put-string~ and the rest of what sift names     |
| ~compat/ice-9/threads.scm~            | a tab is one thread: ~current-processor-count~ answers 1, so ~(sift pool)~ takes its sequential path; every other procedure raises with a sentence |
| ~compat/ice-9/ftw.scm~                | ~scandir~ answers the empty list: there are no directories to walk  |
| ~compat/srfi/srfi-13.scm~             | Hoot has srfi-9, srfi-11 and srfi-14 and no SRFI-13, and Guile's own is written with a ~re-export~ Hoot does not implement; this is the thirteen procedures sift calls, written against ~(scheme base)~ |

The last one is the one worth a paragraph, because the failure it answers is not
obvious.  The core imports SRFI-13 in twenty-six files -- `string-join',
`string-index', `string-trim', `string-prefix?', `string-pad-right' and the rest
-- and a browser build that could not resolve `(srfi srfi-13)' would compile
Guile's own file and stop at `(re-export ...)'.  So the stand-in is a file, and
`tests/web.scm` runs the browser's copy in a second process and fails unless the
format, lint and fix answers it gives are byte-for-byte the answers Guile's
library gives.  A stand-in nobody compares is a second implementation, and a
second implementation is a dialect of its own.

Two names were found the hard way rather than by reading, and are worth a line
each.  ~string-upcase~ and ~string-drop-right~ are Guile procedures that Hoot's
~(guile)~ exports in its export list without defining anywhere: a core module
that reaches for one compiles under Guile, and stops the browser build by name
half way through.  So they are written here, and the test above compares their
answers too.  What no test in this repository can catch is the missing binding
itself -- Guile's own ~(guile)~ answers every name the stand-in does, so a
suite that loads the stand-in under Guile passes whether a name is in it or not.
The gate for that class of failure is ~maak web~, and CI runs it.

Five things were not shimmable, and the source changed instead.  Each change is
one a native build is no worse for, and none of them leaves the browser's name
in the core -- which is the rule the seam above is about:

- *(sift strings)* is new: ~string-find~, ~every-char~, ~string-words~ and
  ~pad-right~ are the four procedures sift needs that R7RS leaves out, written
  against ~string-ref~ and ~string-append~.  Hoot's ~(srfi srfi-13)~ re-exports
  fifty-four names it does not define, and a library whose export list promises
  more than it delivers cannot be completed from outside.  The module is
  portable Scheme with no target in sight, and reads as "what R7RS lacks"
  because that is what it is.
- a ~char-set~ is not a character.  Three call sites built one --
  `(char-set #\space #\tab)` -- because SRFI-13's trim and index procedures
  accept a character, a predicate *or* a character set, and Guile hands
  ~char-set~ to every module.  A character set is an object R7RS does not have,
  so those three pass a predicate of a character instead, which Guile's SRFI-13
  reads the same way and the stand-in reads too.
- ~read-source~ takes its port in the body rather than as a keyword default,
  because a default that calls a procedure is evaluated on every call -- so a
  caller that passes a source and no port was taking a standard input port it
  never read, which is work, and can be a side effect, for nothing.
- ~(sift imports)~ asks the filesystem through three procedures behind a
  ~cond-expand~ whose test is ~(guile ...)~, not ~(hoot ...)~: the question the
  core is asking is "does this Scheme have ~stat~ and ~scandir~?", and the
  answer for a tab is the same as the answer for any Scheme without them -- no
  directory, no names, no text, so ~library-not-found~ never fires, which is the
  truth and not a guess.
- a deadline is measured with R7RS's ~(scheme time)~ -- ~current-jiffy~ and
  ~jiffies-per-second~ -- rather than with ~get-internal-real-time~ and
  ~internal-time-units-per-second~.  Hoot binds neither of the second pair, so
  that spelling compiles under Guile and stops the browser build at
  `make-deadline` by name, and there is no stand-in that could answer it:
  ~(guile)~ is the one module the load path cannot put a file in front of.
  ~(scheme time)~ is the portable spelling of the same question, both
  implementations answer it, and it is monotonic, which is what a bound between
  two steps of a lookup wants.

* How fast it is, honestly

Measured in Chrome 151 on the author's machine, through the page's own request
path, with the whole lint run (all rules for the dialect):

| Buffer    | ~format~ | ~lint~ |
|-----------+----------+--------|
| 300 chars | 17 ms    | 56 ms  |
| 1.2 kB    | 52 ms    | 145 ms |
| 2.4 kB    | 149 ms   | 309 ms |
| 6 kB      | 780 ms   | 1.2 s  |

So a file of a screenful is instant, and a large one is not.  The editor
debounces the lint by 300 ms, which hides the first two rows entirely; past
~2 kB~ you can feel it.  Hoot has no JIT and allocates a record per node, and
the reader allocates four records per character of a Lisp file, so this is the
cost of a Scheme on a Wasm GC and not something the facade can tune away.  If it
matters, ~checkers~ in the request is how to ask for less.

* Checking that it still works

The facade is tested where it runs best -- under Guile, in ~tests/web.scm~, as
part of the ordinary suite:

#+begin_src shell
maak test          # or: guile -L src -L tests -c '(use-modules (tests run)) (run-all!)'
#+end_src

That covers the answers, the failures, the dialects, the styles and the
catalogue, and it is the half of the job that catches a regression in a rule.

The other half is the Wasm build itself, which needs Hoot and a browser.  The
way to check it is to serve ~web/dist/~, open it, and use it -- which is what
was done, in headless Chrome driven over the DevTools protocol: load the page,
wait for the status bar to name a version, then click ~Format~ on
~(define (square x)\n(* x x))~, click ~Fix~ on ~(define (f) (let ((x 1)) x))~,
switch the dialect to Emacs Lisp and format a ~defun~, open ~Rules~, and click a
finding to see the cursor move.

* What is missing, in one list

- No language server.  ~sift lsp~ is a process talking over standard input and
  output; a tab is neither.  Go to definition, hover and the gatherer that
  answers them are all there in ~src/sift/~, and none of it is reachable from
  here yet.
- No project: no ~sift.yaml~, no directory walk, no ~ci~ over a tree.
- No files: the buffer is the unit of work, and there is no "save".
- No ~--force~: a buffer with a parse error is formatted back as it came, with
  the reader's finding in the answer, and the editor shows it.

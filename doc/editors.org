#+title: sift in editors and pipelines
#+author: Josep Bigorra
#+options: toc:2 num:nil
#+language: en

sift is a program to be *called*, not a library to be linked: every
integration below consists of a few lines, because the executable already
speaks the three shapes an editor or a pipeline needs.

| Shape              | What it is for                                              |
|--------------------+-------------------------------------------------------------|
| human              | ~file:line:column: severity: [rule] message~, which every editor's =:make=, =compilation-mode= and every CI log understands |
| =--format=json=    | one array for the run: =file=, =line=, =column=, =checker=, =code=, =severity=, =message= |
| =--format=sarif=   | SARIF 2.1.0, which GitHub code scanning, DefectDojo and the rest read |
| =--format=github=  | workflow commands: =::warning file=…,line=…,col=…,title=SIFT012 [rule]::…= |
| =--format=null=    | nothing at all, for a script that only wants the exit status |

Two conventions carry most of the weight: =--stdin= together with =--label=
checks an unsaved buffer under the name it should carry in the diagnostics,
and =--dialect= names the dialect of a file that is new or has no extension.

* Emacs
:PROPERTIES:
:CUSTOM_ID: emacs
:END:

=emacs/sift.el= is the complete integration: a Flymake backend, code actions,
and a minor mode.  Both entry points, every setting, and the one place where
Emacs knows more than sift does are set out in
[[file:emacs.org][doc/emacs.org]]; the minimal configuration is

#+begin_src elisp
(add-to-list 'load-path "/path/to/sift/emacs")
(require 'sift)
(sift-setup)
(sift-flymake-setup)
#+end_src

after which `C-c s f` formats, `C-c s l` lints into a compilation buffer, `C-c s
x` fixes, `C-c s e` explains the rule under the cursor and `C-c s p` runs the
whole-project check.

The backend is asynchronous, and it retains two facts about the run it started:
the process, so that a question superseded by a new keystroke is cancelled
rather than answered late, and a generation number, so that an answer arriving
after supersession is discarded.  Flymake names an answer to a question no
longer being asked an /obsolete report/, and writes it in *Messages* on every
keystroke; cancellation and numbering prevent that.  Buffer checking and rule
explanation are asynchronous for the same reason -- their result is a message,
and no later command depends on it -- whereas formatting and fixing hold the
text before they return, because the save that follows writes it.

The package itself is optional; =compile= suffices:

#+begin_src elisp
(setq compile-command "sift ci .")
#+end_src

* Emacs, with Eglot
:PROPERTIES:
:CUSTOM_ID: eglot
:END:

sift implements the Language Server Protocol, so Eglot can act as its
client: ~sift lsp~ is a server over standard input and output that publishes
the findings, answers `textDocument/codeAction' with sift's own fixes, and
formats the buffer.  Code actions are the reason to prefer it:
`M-x eglot-code-actions' offers the same edits `sift fix' applies.

#+begin_src elisp
(add-to-list 'load-path "/path/to/sift/emacs")
(require 'sift)
(sift-eglot-setup)
#+end_src

`sift-eglot-setup` registers `sift lsp` in `eglot-server-programs' for the
three Lisp modes, enables `sift-mode` for its keymap and its format-on-save
hook, and withholds from the buffer what the server already performs: the
Flymake backend, since two backends would report every finding twice, and the
format-on-save hook, since the server formats on save, and two formatters
writing one buffer on one save cost two round trips and two undo entries for
one keystroke.

| In an Eglot buffer     | What it does                                            |
|------------------------+---------------------------------------------------------|
| =M-x eglot-code-actions= or =C-c s A= | offer the fixes that apply here             |
| =M-x eglot-format=     | format the buffer through the server                    |
| =C-d= on a finding     | Eglot's own key: the rule's description, and its page   |
| =C-c s f=              | format with the command instead, if you prefer          |

The server asks its client for three things, and each of them is a moment at
which the buffer is checked again:

| What the client sends   | What sift does with it                                |
|-------------------------+-------------------------------------------------------|
| =didOpen=, =didChange=   | lints the buffer, and publishes the findings          |
| =didSave=                | re-reads the saved file, then checks *every* open buffer again: a finding can name a definition in a file nobody has open |
| =didChangeWatchedFiles=  | the same, for a file changed or deleted outside the editor |
| =didChangeConfiguration= | reads =sift.yaml= again -- the line length, the severity floor, which rules run -- and checks every open buffer against it |

Editing =sift.yaml= therefore takes effect in the session already in
progress: after the save, the findings return measured against the new
settings.  The same holds for a definition added in one buffer and jumped to
from another -- the jump is answered from an index the save refreshed, not
from the one the server started with.

The server also reports its own activity at information level over
~window/logMessage~: the root it serves, the dialect each buffer is read as,
the number of findings each report carries, and every re-read it was asked to
perform.  Eglot displays those lines in its own events buffer
(=M-x eglot-events-buffer=), which distinguishes a buffer with no findings from
a server that is not running:

#+begin_example
sift 1.27.1: serving /home/you/src/project
sift: watching the project's Lisp files and its configuration
sift: opened core.scm as scheme
sift: 2 findings in core.scm
sift: re-read core.scm after a save
sift: 1 finding in core.scm
#+end_example

The server is `sift lsp` by default.  When the program is not on the ~PATH~,
`sift-executable` and `sift-eglot-command` name its location;
`sift-eglot-contact` is the function Eglot calls, and it reports a missing
program explicitly.

** Inlay hints

The server answers `textDocument/inlayHint' with the name of a parameter beside
each positional argument of a call whose definition it can resolve, so that
`(make-window root 640 480 "Main")' reads as its own signature without a visit
to `make-window':

#+begin_example
(make-window root parent 640 width 480 height "Main" title)
#+end_example

A hint carries only what sift knows: the definition's own formal list, resolved
by the same mechanism that answers a jump.  A call to a procedure in a library
sift cannot read receives no hint, and neither does an argument that is
already a keyword -- `#:height' states its own name.  Eglot displays hints
once `M-x eglot-inlay-hints-mode' is enabled; Neovim 0.10 and later through
`vim.lsp.inlay_hint.enable(true, { bufnr = bufnr })'.

A hint can also state the type an argument declares outright; the kind is off
by default and enabled with `inlay-hints: [parameters, types]`:

#+begin_example
(make-window root parent 640 width number 480 height number "Main" title string)
#+end_example

This is the entire claim sift makes about types, and the reason the kind is
opt-in: the source must state the type itself.  A string literal is a string,
`#t` is a boolean, `(lambda ...)` is a procedure, `'(1 2)` is a list.  A
variable receives no type hint -- `root` may hold anything, and sift will not
follow it to find out, since a hint that guessed would be worse than none.

** Configuring the server

`sift lsp` reads the same configuration as the rest of sift, plus one further
source.  These settings may appear in a project's `sift.yaml` or in the
editor's own configuration, which is sent to the server and layered over the
files, since the editor's statement is the most specific one that can be made
about this session:

| Setting       | Default      | What it does                                     |
|---------------+--------------+--------------------------------------------------|
| =inlay-hints= | =parameters= | which hints to answer: =parameters= (a parameter's name beside its argument), =types= (the type a literal states), both as a list, or =false= for none |
| =hover=       | =true=       | answer the hover with a rule or a definition     |
| =completion=  | =true=       | offer the names the project defines while typing |

Every other setting reaches the server as well -- `severity`, `line-length`,
`checkers`, `exclude-checkers`, `field-macros` -- because the server computes
its answers from the same configuration the command line reads.  An unknown
key is not a silent no-op: it is reported in the editor's log, so that a typo
in an editor's settings becomes visible.

In Emacs, `eglot-workspace-configuration` is the object Eglot sends:

#+begin_src elisp
(setq-default eglot-workspace-configuration
              '(:sift (:inlay-hints ["parameters" "types"]
                      :field-macros ["package" "operating-system" "my-record"])))
#+end_src

In Neovim, `settings` on the client:

#+begin_src lua
vim.lsp.config("sift", {
  cmd = { "sift", "lsp" },
  root_dir = ...,
  settings = { sift = { ["inlay-hints"] = false } },
})
#+end_src

A change takes effect at once: the server reads its files again under the new
settings and re-checks every open buffer, which is also the path a saved
`sift.yaml` takes.

What a change carries is the editor's *whole* configuration, not the keys that
changed: the object it sends replaces the one the session held, exactly as
`eglot-workspace-configuration` and a client's `settings` are the whole object
the user wrote.  A notification carrying one key therefore drops every other
editor setting back to what the files and the defaults say -- including
`stdlib` and `compiler-diagnostics`, which are the two that read something
outside the buffer.  A client that wants to change one setting sends the
others with it; a client that sends nothing has said nothing, and the project's
own files decide.

Without Eglot the package's Flymake backend provides the integration and
requires nothing else installed:

#+begin_src elisp
(require 'sift)
(sift-setup)
(sift-flymake-setup)
#+end_src

after which `C-c s f` formats, `C-c s l` lints into a compilation buffer, `C-c s
x` fixes, `C-c s e` explains the rule under the cursor and `C-c s p` runs the
whole-project check.

The backend is asynchronous, and it retains two facts about the run it started:
the process, so that a question superseded by a new keystroke is cancelled
rather than answered late, and a generation number, so that an answer arriving
after supersession is discarded.  Flymake names an answer to a question no
longer being asked an /obsolete report/, and writes it in *Messages* on every
keystroke; cancellation and numbering prevent that.  Buffer checking and rule
explanation are asynchronous for the same reason -- their result is a message,
and no later command depends on it -- whereas formatting and fixing hold the
text before they return, because the save that follows writes it.

The package itself is optional; =compile= suffices:

#+begin_src elisp
(setq compile-command "sift ci .")
#+end_src

* Neovim
:PROPERTIES:
:CUSTOM_ID: neovim
:END:

Neovim implements the same protocol, so the integration is a `vim.lsp`
configuration and no plugin.  A complete configuration, to be copied or
required from `init.lua`, is
[[file:../editors/vim/neovim.lua][~editors/vim/neovim.lua~]].

#+begin_src lua
vim.lsp.start({
  name = "sift",
  cmd = { "sift", "lsp" },
  root_dir = vim.fs.dirname(vim.fs.find({ "sift.yaml", ".git" }, { upward = true })[1]),
  on_attach = function(_, bufnr)
    vim.keymap.set("n", "<leader>ca", vim.lsp.buf.code_action, { buffer = bufnr })
    vim.keymap.set("n", "<leader>cf", function() vim.lsp.buf.format() end, { buffer = bufnr })
  end,
})
#+end_src

The root directory is what makes a single server answer for a whole project:
one configuration, one rule set, and one process instead of one per file.

* When a buffer does not parse
:PROPERTIES:
:CUSTOM_ID: broken
:END:

A half-written form is the normal state of a buffer under editing, so every
integration here has an answer for ~(define (f x)~ with the remainder of the
form still to come, and none of them answers by ceasing to work.

| What you ask        | What happens when the text is not a program                   |
|---------------------+---------------------------------------------------------------|
| diagnostics         | the reader's own findings, at severity ~error~, with the code ~reader~ or the parentheses rule that fired: the file is reported, not skipped |
| code actions        | still offered for the findings that do apply; a quickfix only ever edits the span its rule named |
| format              | refused, and *said so*: the server sends ~window/showMessage~ with the reader's reason, and the command exits 2 with the reason on stderr |
| fix                 | refused, the same way: a fix computed around a missing parenthesis would be a guess at where it goes. ~--force~ overrides it for a caller who knows better |
| hover               | whatever rule is on the position, if any                              |

The server can be this tolerant because sift's reader never abandons a file:
~read-source~ returns both the forms it could read *and* the errors it found,
and the linter runs the rules over the forms it obtained.  A buffer with a
broken tail therefore carries findings for its whole beginning, which is what
an editor requires while text is being typed.

The server itself is built to keep answering:

| What goes wrong             | What the server does                                   |
|-----------------------------+--------------------------------------------------------|
| a message that is not JSON  | answers ~-32700~ with a null id, and reads the next one |
| a message with no length    | answers ~-32700~, and reads the next one                |
| a request before initialize | answers ~-32002~, the protocol's own rule              |
| a handler that raises       | answers ~-32603~ (or a ~showMessage~ for a notification) and keeps serving |
| the input closes            | exits 0: an editor that closed the file is not a failure |
| ~exit~ without ~shutdown~    | exits 1, which is how an editor tells a goodbye from a crash |
| a buffer with no language identifier | reads the dialect from the file's own extension, rather than failing to read the buffer at all |
| ~sift.yaml~ saved mid-session, and it does not parse | keeps the configuration it has, says so in the log, and goes on checking the buffers |

The tests for these cases are in ~tests/lsp.scm~, and they address the process
as an editor does: a session is a list of messages on its standard input
together with the frames that return.

* Vim
:PROPERTIES:
:CUSTOM_ID: vim
:END:

Vim carries no language client of its own, so the plugin in
[[file:../editors/vim][~editors/vim/~]] invokes the program.
Copying the directory into `~/.vim`, or pointing a plugin manager at it,
makes the commands available in the Lisp filetypes:

| Command       | What it does                                                  |
|---------------+---------------------------------------------------------------|
| ~:SiftLint~   | fill the quickfix list with the findings, typed and coded      |
| ~:SiftFormat~ | format the buffer, keeping the cursor where it was             |
| ~:SiftFix~    | apply every fix, then lint again                               |
| ~:SiftExplain~ | print what the rule on this line wants                        |

The quickfix list is built from ~--format=json=, so an entry carries the rule
that fired (`SIFT012`), its checker, and its message; `:cnext` walks the list
and `:SiftExplain` opens the rule's page for the entry under the cursor.

For `:make` instead, the compiler plugin is `:compiler sift`:

#+begin_src vim
:compiler sift
:make
#+end_src

which runs `sift ci` over the current file: both questions, one list.
Setting `b:sift_makeprg` to `check` or `lint` before `:make` asks only one of
them.

A Vim project that already has an LSP client plugin — `vim-lsp`, `coc.nvim`,
`ALE` — can point it at `sift lsp` instead, and obtains the same server
Neovim does:

#+begin_src vim
" vim-lsp
if executable('sift')
  au User lsp_setup call lsp#register_server({
        \ 'name': 'sift',
        \ 'cmd': {server_info -> ['sift', 'lsp']},
        \ 'whitelist': ['scheme', 'scheme.guile', 'elisp', 'lisp'],
        \ })
endif
#+end_src

* Visual Studio Code
:PROPERTIES:
:CUSTOM_ID: vscode
:END:

The extension in [[file:../editors/vscode][~editors/vscode/~]] is a pipe:
diagnostics come from ~sift lint --format=json~, quickfixes from ~sift fix~
restricted to the rule that fired, and formatting from ~sift format~.  It has
no dependencies and no build step, so packaging it takes one command:

#+begin_src shell
cd editors/vscode
npx @vscode/vsce package     # writes sift-1.27.1.vsix
code --install-extension sift-1.27.1.vsix
#+end_src

The settings:

| Setting               | Default | Meaning                                                    |
|-----------------------+---------+------------------------------------------------------------|
| ~sift.executable~      | ~sift~  | the program; a bare name is looked up on the PATH          |
| ~sift.severity~        | ~info~  | the lowest severity to report: error, warning or info      |
| ~sift.dialect~         | ~auto~  | auto goes by the extension; or name scheme, elisp or cl    |
| ~sift.lintOn~          | ~change~ | open, change or save                                      |
| ~sift.formatOnSave~    | ~false~ | format before saving                                       |

The commands are `sift: lint this file`, `sift: apply every fix in this file`,
and `sift: explain the rule at the cursor`.  A quickfix is attached to a
finding and runs `sift fix --checker=<rule>`, so that it applies *that* rule
alone and not every rule at once; the edit it applies is the smallest range
that differs.

A project that prefers no extension can point any generic language client
extension at `sift lsp`, and obtains the same server as the other two editors.

* Git hooks
:PROPERTIES:
:CUSTOM_ID: hooks
:END:

=sift install-hooks= writes a =pre-commit= hook that runs ~sift ci~ over the
repository.  A hook that checks only what is being committed takes this form:

#+begin_src shell
#!/bin/sh
files=$(git diff --cached --name-only --diff-filter=ACM | grep -E '\.(scm|ss|sld|sls|el|lisp|cl|asd)$' || true)
[ -z "$files" ] && exit 0
sift check $files || {
  echo "sift: run \`sift format --write $files' and stage the result"
  exit 1
}
#+end_src

Under the [[https://pre-commit.com][pre-commit]] framework, the repository's
=.pre-commit-hooks.yaml= declares =sift-format= (rewrites), =sift-check=
(fails), and =sift-lint=:

#+begin_src yaml
repos:
  - repo: https://github.com/jjba23/sift
    rev: v1.27.1
    hooks: [{id: sift-format}, {id: sift-lint}]
#+end_src

* Continuous integration
:PROPERTIES:
:CUSTOM_ID: ci
:END:

One command asks both questions, and the exit status carries the answer:

#+begin_src shell
sift ci src/ tests/
#+end_src

** The reusable workflow

A repository that wants sift in its pipeline writes one file and receives both
halves of the answer: annotations on the lines of the pull request, and a
SARIF document in the Security tab.

#+begin_src yaml
# .github/workflows/sift.yml
name: sift
on: [push, pull_request]
jobs:
  sift:
    uses: jjba23/sift/.github/workflows/sift.yml@v1.27.1
#+end_src

The workflow takes inputs, all of them optional:

| input             | default      | meaning                                                        |
|-------------------+--------------+----------------------------------------------------------------|
| ~paths~           | ~.~          | files or directories to judge, space separated                 |
| ~mode~            | ~ci~         | ~ci~ formats and lints, ~lint~ only lints, ~check~ only checks |
| ~severity~        | ~warning~    | lowest severity to report: ~error~, ~warning~ or ~info~        |
| ~install~         | ~guix~       | ~guix~ builds the checkout, ~path~ uses a sift on the PATH     |
| ~sarif-file~      | ~sift.sarif~ | where the SARIF document goes, empty for none                  |
| ~fail-on-findings~ | ~true~       | ~false~ reports the findings and passes the job                |
| ~upload-sarif~    | ~true~       | upload the document to code scanning                           |
| ~sift-ref~        | ~main~       | which revision of sift provides the action                     |

Two permissions matter.  The job requests =security-events: write= so that the
upload can occur; a caller that has narrowed the workflow's permissions must
allow it as well, in which case the findings remain annotations and only the
upload step fails.

** The action on its own

The workflow is a caller of =action.yml= at the root of the repository, a
composite action that a job can use beside its other steps:

#+begin_src yaml
- uses: actions/checkout@v4
- uses: jjba23/sift@v1.27.1
  with:
    paths: src/ tests/
    severity: warning
- uses: github/codeql-action/upload-sarif@v3
  if: always()
  with:
    sarif_file: sift.sarif
#+end_src

It takes the same inputs as the workflow, except ~upload-sarif~ and
~sift-ref~, and produces two outputs: ~sarif-file~, and ~findings~, the
number of findings the document holds.  The action never uploads anything
itself: a step that silently required a permission the caller did not grant
would fail for a reason unrelated to the code being judged.

The work is done by [[file:../ci/sift-action.sh][=ci/sift-action.sh=]], a POSIX shell script this file only
wraps, so the action can be run and tested without a runner:

#+begin_src shell
SIFT_INSTALL=path SIFT_PATHS=src/ ./ci/sift-action.sh
#+end_src

** Without the action

The same two answers, spelled out.  =--format=github= turns each finding into
an annotation on the pull request:

#+begin_src yaml
- name: sift
  run: ./bin/sift ci --format=github src/
#+end_src

=--format=sarif= writes a document that GitHub code scanning reads, which is
what places the findings in the repository's Security tab.  The document
covers the whole run, whichever mode requested it, and is therefore safe to
redirect to a file:

#+begin_src yaml
- name: sift (SARIF)
  run: ./bin/sift ci --format=sarif src/ > sift.sarif

- name: Upload SARIF
  uses: github/codeql-action/upload-sarif@v3
  if: always()
  with:
    sarif_file: sift.sarif
#+end_src

A job that needs only a pass or a fail uses =--format=null=, which prints
nothing and keeps the exit status:

#+begin_src shell
sift ci --format=null . || exit 1
#+end_src

* Deciding what fails
:PROPERTIES:
:CUSTOM_ID: thresholds
:END:

A pipeline fails on what the project calls wrong, and on nothing else.  The
threshold is the severity:

#+begin_src shell
sift ci --severity=error .    # only errors stop the build
sift ci --severity=warning .  # warnings too; the usual choice
sift ci .                     # everything, suggestions included
#+end_src

Most projects settle on =warning= and record it in the repository rather than
in a flag, so that the local run and the CI run agree:

#+begin_src yaml
# sift.yaml
severity: warning
#+end_src

This repository does so, and =sift doctor= reports which layer decided the
value:

#+begin_src shell
$ sift doctor
sift 1.27.1
  guile       3.0.11
  library     /home/joe/Hacking/sift/src
  rules       39
  dialects    scheme, elisp, cl

Configuration
  project  /home/joe/Hacking/sift/sift.yaml

Settings that are not the default
  brackets: square  # /home/joe/Hacking/sift/sift.yaml
  severity: warning  # /home/joe/Hacking/sift/sift.yaml
#+end_src

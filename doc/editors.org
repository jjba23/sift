#+title: sift in editors and pipelines
#+author: Josep Bigorra
#+options: toc:2 num:nil
#+language: en

sift was built to be *called*, not to be a monolith: every integration below
is a few lines, because the program already speaks the three shapes an editor
or a pipeline needs.

| Shape              | What it is for                                              |
|--------------------+-------------------------------------------------------------|
| human              | ~file:line:column: severity: [rule] message~, which every editor's =:make=, =compilation-mode= and every CI log understands |
| =--format=json=    | one array for the run: =file=, =line=, =column=, =checker=, =code=, =severity=, =message= |
| =--format=sarif=   | SARIF 2.1.0, which GitHub code scanning, DefectDojo and the rest read |
| =--format=github=  | workflow commands: =::warning file=…,line=…,col=…,title=SIFT012 [rule]::…= |
| =--format=null=    | nothing at all, for a script that only wants the exit status |

Two habits make any integration a pleasant one: pass =--stdin= with a
=--label= so that an unsaved buffer can be checked with the right name in the
diagnostics, and pass =--dialect= when the file is new or has no extension.

* Emacs
:PROPERTIES:
:CUSTOM_ID: emacs
:END:

=emacs/sift.el= is the full integration: a Flymake backend, code actions and a
minor mode.  It is described in the README; the short version is

#+begin_src elisp
(add-to-list 'load-path "/path/to/sift/emacs")
(require 'sift)
(sift-setup)
(sift-flymake-setup)
#+end_src

and then `C-c s f` formats, `C-c s l` lints into a compilation buffer, `C-c s
x` fixes, `C-c s e` explains the rule under the cursor and `C-c s p` runs the
whole-project check.

If you would rather not load the package, =compile= is enough:

#+begin_src elisp
(setq compile-command "sift ci .")
#+end_src

* Emacs, with Eglot
:PROPERTIES:
:CUSTOM_ID: eglot
:END:

sift speaks the Language Server Protocol, so Eglot can talk to it: ~sift lsp~
is a server on standard input and output that reports the findings, answers
`textDocument/codeAction' with sift's own fixes, and formats the buffer.  That
is the integration with *code actions* — `M-x eglot-code-actions' offers the
same edits `sift fix' applies.

#+begin_src elisp
(add-to-list 'load-path "/path/to/sift/emacs")
(require 'sift)
(sift-eglot-setup)
#+end_src

`sift-eglot-setup` teaches `eglot-server-programs' about the three Lisp modes,
turns `sift-mode` on for its keymap and its format-on-save hook, and keeps the
Flymake backend out of the way: two backends would report every finding twice.

| In an Eglot buffer     | What it does                                            |
|------------------------+---------------------------------------------------------|
| =M-x eglot-code-actions= or =C-c s A= | offer the fixes that apply here             |
| =M-x eglot-format=     | format the buffer through the server                    |
| =C-d= on a finding     | Eglot's own key: the rule's description, and its page   |
| =C-c s f=              | format with the command instead, if you prefer          |

The server is `sift lsp` by default.  If the program is not on your ~PATH~,
`sift-executable` and `sift-eglot-command` say where it is; `sift-eglot-contact`
is what Eglot calls, and it says so plainly when the program is missing.

Without Eglot, the package's Flymake backend is the integration and needs
nothing installed:

#+begin_src elisp
(require 'sift)
(sift-setup)
(sift-flymake-setup)
#+end_src

and then `C-c s f` formats, `C-c s l` lints into a compilation buffer, `C-c s
x` fixes, `C-c s e` explains the rule under the cursor and `C-c s p` runs the
whole-project check.

If you would rather not load the package, =compile= is enough:

#+begin_src elisp
(setq compile-command "sift ci .")
#+end_src

* Neovim
:PROPERTIES:
:CUSTOM_ID: neovim
:END:

Neovim speaks the same protocol as Eglot, so the integration is a `vim.lsp`
configuration and no plugin at all.  [[file:../editors/vim/neovim.lua][~editors/vim/neovim.lua~]] is a complete
one: copy it, or require it from `init.lua`.

#+begin_src lua
vim.lsp.start({
  name = "sift",
  cmd = { "sift", "lsp" },
  root_dir = vim.fs.dirname(vim.fs.find({ "sift.yaml", ".git" }, { upward = true })[1]),
  on_attach = function(_, bufnr)
    vim.keymap.set("n", "<leader>ca", vim.lsp.buf.code_action, { buffer = bufnr })
    vim.keymap.set("n", "<leader>cf", function() vim.lsp.buf.format() end, { buffer = bufnr })
  end,
})
#+end_src

The root directory is what makes one server answer for a whole project: the
same configuration, the same rules, and one process instead of one per file.

* When a buffer does not parse
:PROPERTIES:
:CUSTOM_ID: broken
:END:

A half-written form is the normal state of a buffer being typed, so every
integration here has an answer for ~(define (f x)~ with the rest of the form
still to come, and none of them is "stop working".

| What you ask        | What happens when the text is not a program                   |
|---------------------+---------------------------------------------------------------|
| diagnostics         | the reader's own findings, at severity ~error~, with the code ~reader~ or the parentheses rule that fired: the file is reported, not skipped |
| code actions        | still offered for the findings that do apply; a quickfix only ever edits the span its rule named |
| format              | refused, and *said so*: the server sends ~window/showMessage~ with the reader's reason, and the command exits 2 with the reason on stderr |
| fix                 | refused, the same way: a fix computed around a missing parenthesis would be a guess at where it goes. ~--force~ overrides it for a caller who knows better |
| hover               | whatever rule is on the position, if any                              |

The reason the language server can be this relaxed is that sift's reader
never abandons a file: ~read-source~ returns the forms it could read *and*
the errors it found, and the linter runs the rules over what it got.  A buffer
with a broken tail therefore has findings for its whole beginning, which is
what an editor needs while someone is typing.

The server itself is written to keep answering:

| What goes wrong             | What the server does                                   |
|-----------------------------+--------------------------------------------------------|
| a message that is not JSON  | answers ~-32700~ with a null id, and reads the next one |
| a message with no length    | answers ~-32700~, and reads the next one                |
| a request before initialize | answers ~-32002~, the protocol's own rule              |
| a handler that raises       | answers ~-32603~ (or a ~showMessage~ for a notification) and keeps serving |
| the input closes            | exits 0: an editor that closed the file is not a failure |
| ~exit~ without ~shutdown~    | exits 1, which is how an editor tells a goodbye from a crash |

The tests for all of that are in ~tests/lsp.scm~, and they talk to the process
the way an editor does: a session is a list of messages on its standard input
and the frames that come back.

* Vim
:PROPERTIES:
:CUSTOM_ID: vim
:END:

Vim has no language client of its own, so the plugin in
[[file:../editors/vim][~editors/vim/~]] calls the program.  Copy the directory into `~/.vim`, or point a
plugin manager at it, and the commands appear in the Lisp filetypes:

| Command       | What it does                                                  |
|---------------+---------------------------------------------------------------|
| ~:SiftLint~   | fill the quickfix list with the findings, typed and coded      |
| ~:SiftFormat~ | format the buffer, keeping the cursor where it was             |
| ~:SiftFix~    | apply every fix, then lint again                               |
| ~:SiftExplain~ | print what the rule on this line wants                        |

The quickfix list is built from ~--format=json=, so an entry says which rule
fired (`SIFT012`), which checker it is, and what it wants; `:cnext` walks them
and `:SiftExplain` reads the rule's page for the one under the cursor.

For `:make` instead, the compiler plugin is `:compiler sift`:

#+begin_src vim
:compiler sift
:make
#+end_src

which runs `sift ci` over the current file: both questions, one list.  Set
`b:sift_makeprg` to `check` or `lint` before `:make` to ask only one of them.

Vim projects that already have an LSP client plugin — `vim-lsp`, `coc.nvim`,
`ALE` — can point it at `sift lsp` instead, and get the same server Neovim
gets:

#+begin_src vim
" vim-lsp
if executable('sift')
  au User lsp_setup call lsp#register_server({
        \ 'name': 'sift',
        \ 'cmd': {server_info -> ['sift', 'lsp']},
        \ 'whitelist': ['scheme', 'scheme.guile', 'elisp', 'lisp'],
        \ })
endif
#+end_src

* Visual Studio Code
:PROPERTIES:
:CUSTOM_ID: vscode
:END:

The extension in [[file:../editors/vscode][~editors/vscode/~]] is a pipe and nothing else: diagnostics come
from ~sift lint --format=json~, quickfixes from ~sift fix~ for the rule that
fired, and formatting from ~sift format~.  It has no dependencies and no build
step, so packaging it is one command:

#+begin_src shell
cd editors/vscode
npx @vscode/vsce package     # writes sift-1.1.0.vsix
code --install-extension sift-1.1.0.vsix
#+end_src

The settings:

| Setting               | Default | Meaning                                                    |
|-----------------------+---------+------------------------------------------------------------|
| ~sift.executable~      | ~sift~  | the program; a bare name is looked up on the PATH          |
| ~sift.severity~        | ~info~  | the lowest severity to report: error, warning or info      |
| ~sift.dialect~         | ~auto~  | auto goes by the extension; or name scheme, elisp or cl    |
| ~sift.lintOn~          | ~change~ | open, change or save                                      |
| ~sift.formatOnSave~    | ~false~ | format before saving                                       |

The commands are `sift: lint this file`, `sift: apply every fix in this file`,
and `sift: explain the rule at the cursor`.  A quickfix appears on a finding,
and it runs `sift fix --checker=<rule>` so that it fixes *that* rule and not
every rule at once; the edit it applies is the smallest range that differs.

A project that would rather not install an extension can point any generic
language client extension at `sift lsp`, and get the server the other two
editors get.

* Git hooks
:PROPERTIES:
:CUSTOM_ID: hooks
:END:

=sift install-hooks= writes a =pre-commit= hook that runs ~sift ci~ over the
repository.  For a hook that checks only what is being committed:

#+begin_src shell
#!/bin/sh
files=$(git diff --cached --name-only --diff-filter=ACM | grep -E '\.(scm|ss|sld|sls|el|lisp|cl|asd)$' || true)
[ -z "$files" ] && exit 0
sift check $files || {
  echo "sift: run \`sift format --write $files' and stage the result"
  exit 1
}
#+end_src

With the [[https://pre-commit.com][pre-commit]] framework, the repository's
=.pre-commit-hooks.yaml= declares =sift-format= (rewrites), =sift-check=
(fails) and =sift-lint=:

#+begin_src yaml
repos:
  - repo: https://github.com/jjba23/sift
    rev: v1.1.0
    hooks: [{id: sift-format}, {id: sift-lint}]
#+end_src

* Continuous integration
:PROPERTIES:
:CUSTOM_ID: ci
:END:

One command asks both questions, and the exit status is the answer:

#+begin_src shell
sift ci src/ tests/
#+end_src

** The reusable workflow

A repository that wants sift in its pipeline writes one file and gets both
halves of the answer: annotations on the lines of the pull request, and a
SARIF document in the Security tab.

#+begin_src yaml
# .github/workflows/sift.yml
name: sift
on: [push, pull_request]
jobs:
  sift:
    uses: jjba23/sift/.github/workflows/sift.yml@v1.1.0
#+end_src

The workflow takes inputs, all of them optional:

| input             | default      | meaning                                                        |
|-------------------+--------------+----------------------------------------------------------------|
| ~paths~           | ~.~          | files or directories to judge, space separated                 |
| ~mode~            | ~ci~         | ~ci~ formats and lints, ~lint~ only lints, ~check~ only checks |
| ~severity~        | ~warning~    | lowest severity to report: ~error~, ~warning~ or ~info~        |
| ~install~         | ~guix~       | ~guix~ builds the checkout, ~path~ uses a sift on the PATH     |
| ~sarif-file~      | ~sift.sarif~ | where the SARIF document goes, empty for none                  |
| ~fail-on-findings~ | ~true~       | ~false~ reports the findings and passes the job                |
| ~upload-sarif~    | ~true~       | upload the document to code scanning                           |
| ~sift-ref~        | ~main~       | which revision of sift provides the action                     |

Two permissions matter.  The job asks for =security-events: write= so that the
upload can happen; a caller that has narrowed the workflow's permissions must
allow it too, and the findings are then still annotations, with the upload as
the only step that fails.

** The action on its own

The workflow is a caller of =action.yml= at the root of the repository, which
is a composite action a job can use beside its other steps:

#+begin_src yaml
- uses: actions/checkout@v4
- uses: jjba23/sift@v1.1.0
  with:
    paths: src/ tests/
    severity: warning
- uses: github/codeql-action/upload-sarif@v3
  if: always()
  with:
    sarif_file: sift.sarif
#+end_src

It takes the same inputs as the workflow, minus ~upload-sarif~ and
~sift-ref~, and answers with two outputs: ~sarif-file~, and ~findings~, the
number of findings the document holds.  The action never uploads anything
itself, because a step that quietly needs a permission the caller did not
grant fails for a reason that has nothing to do with the code being judged.

The work is done by [[file:../ci/sift-action.sh][=ci/sift-action.sh=]], a POSIX shell script this file only
wraps, so the action can be run and tested without a runner:

#+begin_src shell
SIFT_INSTALL=path SIFT_PATHS=src/ ./ci/sift-action.sh
#+end_src

** Without the action

The same two answers, spelled out.  =--format=github= turns each finding into
an annotation on the pull request:

#+begin_src yaml
- name: sift
  run: ./bin/sift ci --format=github src/
#+end_src

=--format=sarif= writes a document that GitHub code scanning reads, which is
what puts the findings in the repository's Security tab.  It is one document
for the whole run, whichever mode asked for it, which is what makes it safe to
redirect to a file:

#+begin_src yaml
- name: sift (SARIF)
  run: ./bin/sift ci --format=sarif src/ > sift.sarif

- name: Upload SARIF
  uses: github/codeql-action/upload-sarif@v3
  if: always()
  with:
    sarif_file: sift.sarif
#+end_src

The job that only needs a pass or a fail uses =--format=null=, which prints
nothing and keeps the status:

#+begin_src shell
sift ci --format=null . || exit 1
#+end_src

* Deciding what fails
:PROPERTIES:
:CUSTOM_ID: thresholds
:END:

A pipeline should fail on what the project calls wrong, and only on that.  The
dial is the severity:

#+begin_src shell
sift ci --severity=error .    # only errors stop the build
sift ci --severity=warning .  # warnings too; the usual choice
sift ci .                     # everything, suggestions included
#+end_src

Most projects settle on =warning= and put it in the repository rather than in
a flag, so that the local run and the CI run agree:

#+begin_src yaml
# sift.yaml
severity: warning
#+end_src

That is what this repository does, and =sift doctor= is how you check which
layer decided it:

#+begin_src shell
$ sift doctor
sift 1.1.0
  guile       3.0.11
  library     /home/joe/Hacking/sift/src
  rules       39
  dialects    scheme, elisp, cl

Configuration
  project  /home/joe/Hacking/sift/sift.yaml

Settings that are not the default
  brackets: square  # /home/joe/Hacking/sift/sift.yaml
  severity: warning  # /home/joe/Hacking/sift/sift.yaml
#+end_src

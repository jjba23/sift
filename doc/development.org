The commands behind the ~maak~ tasks, the pipeline those tasks run in, the
quantities the benchmarks measure, and the dependency order of the modules.
Every gate listed here is a gate the release runs.

* Testing
:PROPERTIES:
:CUSTOM_ID: testing
:END:

No part of the project is tested with a bespoke harness: the library runs
under Veritas, the Emacs package under ERT, the editors under the framework
each one ships, and none of those suites is a smoke test.

The library is tested with [[https://codeberg.org/jjba23/veritas][Veritas]], and with nothing else: no ~srfi-64~,
no ad-hoc assertion macro anywhere in the tree.  Veritas is expected at
~$HOME/Hacking/veritas~, or wherever ~VERITAS_DIR~ points, and ~maak test~
places it on the load path itself, so that a clean checkout needs no exports:

#+begin_src shell
maak test          # the whole Veritas suite
maak check         # compile every module, so a syntax error fails the build
maak self-check    # sift's own sources are formatted by sift
maak fixture-check # the golden corpus still round-trips, byte for byte
maak docs          # regenerate doc/rules.org from the rules
maak bench         # time the reader, the formatter and every checker
#+end_src

~maak test~ is intended to run inside the pinned environment, so that the
Guile, the JSON library and Veritas are the versions against which the project
is developed:

#+begin_src shell
guix time-machine --channels=channels.scm -- shell -m manifest.scm
#+end_src

~maak bench~ is Veritas as well: a benchmark is a task whose result is a
~benchmark-result~, so it is printed by the same reporter as every other test,
and the table it ends with is sorted worst first.  It times what a user waits
for -- reading a file, formatting it, linting it, and the same over the whole
tree -- and then the passes of which those are composed, so that a regression
has a place to point.  Two numbers are reported per benchmark, and both are
significant: the milliseconds, and the bytes allocated.  A pass that conses a
list per node makes every other pass slower, and the allocation count is how
that cost appears even when the clock happens to look favourable.

#+begin_src shell
$ maak bench
lint the tree (28 files, 14896 lines)       337ms, 160.7 MiB allocated
check the tree (28 files): format           253ms,  59.0 MiB allocated
lint (lsp.scm, every checker)               171ms,  19.2 MiB allocated
read the tree (28 files)                    143ms,  44.7 MiB allocated
checker: unused-argument                      9ms, 793.0 KiB allocated
...
#+end_src

#+begin_src shell
maak bench tests   # time the test suite's sources instead of src
SIFT_BENCHMARK_PATHS=src:benchmarks maak bench
#+end_src

Each editor is tested with the test framework it ships:

#+begin_src shell
maak emacs-test     # ERT: the package, its Flymake backend and its Eglot entry
maak emacs-check    # byte-compile, warnings are errors
maak editors-check  # Vim in batch over the plugin, Node over the VS Code logic
#+end_src

~maak editors-check~ requires ~vim~ and ~node~, and nothing else: the Vim test
sources the plugin and drives it through ~:SiftLint~ and ~:SiftFix~, and the
VS Code test executes the extension's own arithmetic — the ranges a quickfix
replaces — against Node's ~assert~.

The suite is neither a smoke test nor a single file.  The reader is tested
dialect by dialect on every reader macro, every escape, CRLF and UTF-8
columns; the formatter on a golden corpus in both styles plus an idempotence
pass over every expected file; each rule has a file of its own, with a passing
case, a failing case at a known line and column, one case per applicable
dialect, and — where the rule has a fix — the fixed text and a re-lint that
must find nothing; the command line is tested as a subprocess, by exit status;
and the language server is tested by being talked to, a frame at a time,
including the frames that are not JSON.

A language-server session in the suite is the whole conversation: the messages
are written to the process before it starts, and what comes back is unframed the
way an editor reads it, so the wire is under test and not one handler behind it.
Two defaults keep such a test about what it names.  The standard library is off
-- what a machine happens to have installed is not something a test can assert,
and reading a thousand library files is a test that takes a minute.  The
compiler is off as well, and a test that sends settings of its own restates both
rather than sending only the key it is about: an editor's settings arrive as one
object, so a notification carrying one key drops the other two back to their
defaults, and a compile started that way reports from a thread of its own.  A
test counting publications would then be counting a compile.

* Continuous integration, and how a release is cut
:PROPERTIES:
:CUSTOM_ID: continuous-integration
:END:

The pipeline is [[file:../.github/workflows/ci.yml][.github/workflows/ci.yml]], and it has no steps of its own:
each job hands a list of ~maak~ tasks to the
[[https://github.com/jjba23/byggsteg-github][Byggsteg]] deployment, which clones
the repository and runs them there -- and a task that needs Guile runs itself
inside ~guix time-machine --channels=channels.scm -- shell -m manifest.scm~, so
the Guile that builds a branch is the Guile the branch is developed against.

Two jobs, because a gate and a deployment are two different questions:

- *gates* asks whether the tree is worth merging: ~maak test~, ~maak check~,
  ~maak self-check~, ~maak fixture-check~, ~maak emacs-check~ and
  ~maak emacs-test~.  That is what ~maak release~ runs, minus ~docs~ -- the
  suite already fails when ~doc/rules.org~ is not what the rules produce.  It
  runs on a push to ~trunk~, on a pull request against it, and on a dispatch,
  so a branch is judged before it lands rather than after it fails.  A pull
  request from a fork is skipped, because the daemon clones the repository the
  run belongs to and a branch that exists only in the fork is not there; the
  push that follows the merge is the run that judges that tree.
- *deploy* publishes the browser build, and it needs ~gates~ to have passed:
  ~maak web-deploy~ copies what ~maak web~ built into the directory the server
  serves.  That is a deployment and not a check, so it runs for a push to
  ~trunk~ or a dispatch and never for a pull request.  A build published from a
  tree that failed its own checks is a build the site has to take back.

A release is cut from a green tree, by the one task that also runs the gates:

#+begin_src shell
maak release 1.28.0   # version everywhere, every gate, the commit and the tag
git push origin trunk --follow-tags
gh release create v1.28.0 --title "sift 1.28.0 — ..."   # the release notes
#+end_src

The number is stated once, as ~sift-version~ in ~src/sift/records.scm~, and
quoted in the Emacs package, the README badge, the pre-commit hooks, the
action's sample, the reusable workflow and the VS Code extension; ~maak
version~ lists every one of them, and ~maak release~ rewrites the number inside
the shapes it knows and touches nothing else.  The gates run before the commit
rather than after it, so a release that would have been broken is a tree with a
new number in it and a message saying which check said no -- never a tag that
has to be taken back.  A tag is published when it is pushed with the commit it
names, and the notes are the GitHub release for that tag.

* How it is built
:PROPERTIES:
:CUSTOM_ID: architecture
:END:

#+begin_example
src/sift/
  records.scm       <source-location>, <lint-warning>, <lint-checker>, rule
                    codes, and the uniform AST node
  reader.scm        the hand-written, permissive, location-preserving reader
  format.scm        the pipeline, the indentation tables, the renderer
  check/base.scm    walking a tree, reading a form, line arithmetic
  complexity.scm    how much a definition asks of a reader
  checkers/         one module per family of rules
  pool.scm          the work spread over the processors, answered in order
  lint.scm          run, suppress, filter, sort, fix, re-lint
  render.scm        human, JSON, GitHub, null, SARIF, list-checkers, explain, diff
  config.scm        <config>, discovery, merging, provenance, trust
  yaml.scm          the data-only YAML subset the configuration needs
  json.scm          the JSON the language server speaks
  definitions.scm   what defines a name, what binds one, and where it is used
  files.scm         which files are Lisp files, and reading a compressed one
  imports.scm       import forms and the libraries a project declares
  analysis.scm      the LSP questions that are a function of a buffer
  stdlib.scm        the library an implementation ships, indexed for navigation
  sources.scm       downloading, checking and caching a source archive
  compiler.scm      the dialect's own compiler, asked for a second opinion
  lsp.scm           diagnostics, actions, formatting, hover, and navigation
  catalogue.scm     the rule catalogue, generated from the records
  cli.scm           args-fold, dispatch, exit codes
tests/              one Veritas suite per rule, per module and per command
benchmarks/         the benchmarks, run by Veritas and printed by its reporter
emacs/              the Emacs package and its ERT suite
editors/            the Neovim, Vim and VS Code integrations, with their tests
assets/             the logo, the app icon set and the demo recording
doc/                style.org (the reasoning), rules.org (generated),
                    formatting.org (the formatter), linting.org (the rules
                    runner), editors.org (every editor), emacs.org (the Emacs
                    package), cli.org (the command line),
                    language-server.org (the protocol),
                    configuration.org (the settings), design.org (why),
                    development.org (this page)
#+end_example

Dependencies point one way.  ~records~ is a vocabulary; ~reader~ and ~format~
use it; the checkers use ~records~ and ~check/base~; ~lint~ assembles the
checkers; ~render~ formats their findings; ~lsp~ turns the same findings into a
protocol; ~cli~ wires everything to the command line.  Nothing in ~format~ or
in a checker knows about ports or exit codes.

A contribution follows from that order: a rule is a record in a checker module
together with a test that names its line and column; a fix is a procedure over
one range; and a change to the language server changes how the same findings
are said, rather than adding a second implementation of them.

FORMAT THE FORM, NOT THE PROGRAM — every choice below changes how a Lisp file is read, never what it does.

Why a style at all

A Lisp is written for two readers: the compiler, and a person scanning a buffer for the shape of the program. The second reader is the one a style serves. Lisp's advantage over other languages is that its structure is visible — parentheses, and nothing else — and a formatter that respects that structure makes the shape obvious at a glance.

sift enforces a style because a project with two styles has none. But it enforces it in the narrowest way it can: it moves whitespace and delimiter characters, and it suggests what a human should do next. It never rewrites an expression's meaning, never reflows a form, and never fixes anything without being asked.

The three principles behind every rule:

  1. The tree is the truth. Indentation follows the nesting, not the author's earlier indentation. That is why formatting is idempotent.
  2. Nothing is lost. A comment, a blank line and a `'` are content, not noise; the formatter carries them through.
  3. Say what you mean, once. `when` instead of `(if x y)`, `unless` instead of `(if (not x) y)`, `let` instead of a paragraph-long expression, `:key` instead of the sixth positional argument.

The ten choices

Two columns

Every body indents two columns from the opening parenthesis: 

(define (square x)
  (* x x))

(let ((a 1)
      (b 2))
  (+ a b))

Why two? A Lisp line starts with a form and its operator; two columns is the smallest step that is visibly a step, and it leaves the most room for the form itself. It is what Emacs Lisp's own manual shows, what the Scheme standard's examples show, and what every Lisp I have read for thirty years does. Four columns make a nested form run off the right edge; one column is not a step at all.

The one exception is a data list — a binding list, a vector, a quoted structure — whose elements line up under the first element: 

(let ((short 1)
      (a-much-longer-name 2))
  ...)

Why? Those elements are not a body; they are a column of things, and a column is easier to scan when it is aligned.

One blank line between top-level forms

Forms at top level are separated by at most one blank line, and runs of three or more inside a form are collapsed to two. sift never inserts a blank line where there was none: the author's grouping survives.

Why? A blank line is a paragraph break. In Lisp, a top-level form is a paragraph, and two forms that belong together are separated by one. Three blank lines mean the same as one, at four times the cost.

Closing delimiters trail — by default

(define (f x)
  (if (null? x)
      '()
      (cons (car x)
            (f (cdr x)))))

The alternative, `–style=dangling`, puts each closer on its own line, aligned with its opener: 

(define (f x)
  (if (null? x)
      '()
      (cons (car x)
            (f (cdr x))
      )
  )
)

Why is trailing the default? Because it is what every Lisp community does, and because a closer that trails is a closer you can see closing something. A line holding only `)` is a line that carries no information except "one form ended somewhere above" — which the indentation already told you. Emacs Lisp code never dangles; Common Lisp style guides say not to; Scheme code does not. Dangling is available because a project that has already chosen it should not have to fight the formatter, but it is opt-in.

Square brackets for `cond` clauses, in Scheme

(cond [(< n 0) 'negative]
      [(= n 0) 'zero]
      [else 'positive])

Why? A `cond` clause is not a call: it is a pair of test and body, and the bracket says where the pair ends without asking the reader to count parentheses. Guile's own sources and the Guix code base write it this way, and since Scheme reads `[` and `(` interchangeably, the change is purely visual — which is the only kind of change a formatter may make.

sift applies it to the clause lists of `cond` (and `case`, when the project asks for it), and nowhere else: a binding list is already aligned, and turning every list into a bracket would be noise. A project that prefers parentheses sets `brackets: parens`, or runs `–brackets=parens`; a project that wants to keep whatever is written sets `brackets: preserve`.

It never applies to Emacs Lisp or Common Lisp, whatever the setting says: a square bracket is not syntax in either, so a `sift.yaml` that asks for square brackets and a directory that holds an `.el` file would otherwise produce a file Emacs cannot read. The setting is about Scheme because the argument for it is about Scheme.

Keyword arguments line up

A call that passes keyword arguments lines them up under its first argument: 

(make-window title
             :width 10
             :height 20)

Why? The keywords become a column of names and values instead of a staircase, and the reader can compare two calls by looking down the same column. It is what Emacs does for a call it knows, and what a reader does for a call they do not.

A project's macros are the project's business

When a macro is not in sift's table, sift indents it by the generic rule; when a project knows better, it says so in its configuration: 

indent-rules:
  - [with-my-thing, 2]
  - [deftransaction, 1]

A project rule wins over the built-in table, so a local convention can be expressed without patching the tool.

No reflowing

sift never moves a line break that the author put somewhere structurally meaningful, and it never joins two lines that the author split. It fixes indentation and spacing on the lines that exist.

Why? Line breaks in Lisp are where the author decided a form was getting long. A pretty-printer that re-decides them produces diffs that are not about the change being made, and a formatter whose diffs nobody reads is a formatter nobody runs. It also means the formatter is safe on a file being edited: it cannot move a line out from under a cursor.

Reader prefixes are glued to their datum

`'foo`, `` `(a ,b) ``, `#'bar`, `#+sbcl …` and `#.(…)` are one unit. The formatter closes any gap between a prefix and its datum, and `reader-prefix-break` (SIFT007) reports a file that has one.

Why? A prefix is not a form; it is part of the next form's name. A line break between them reads as a break at the wrong level, and in Common Lisp a whitespace-sensitive feature expression makes it a real hazard.

Comments stay on their line

An inline comment stays on the line it was written on, one space after the code — or aligned across a run of contiguous lines when `–comment-align` is on: 

(let ((a 1)    ; the first
      (b 22))  ; and the second
  (+ a b))

A standalone comment keeps its own line and takes the indentation of the form it is in.

Why? A comment's position is its meaning: `; the default is 0` on the line of a binding is about that binding. Moving it is editing the program's documentation, which no formatter should do silently.

Docstrings are documentation, not decoration

The first line is a capitalised sentence ending in a period and short enough to fit in `apropos` (74 columns in Emacs Lisp). The first sentence is in the imperative — "Return the value", not "Returns the value". Continuation lines start at column zero of the string. In Emacs Lisp the arguments are named in the docstring; in Guile they are written with `@var{}` so the manual typesets them as metavariables. 

(defun add (a b)
  "Add A and B.

Return the sum, which is a number."
  (+ a b))

(define (add a b)
  "Add @var{a} and @var{b}.

Return the sum, which is a number."
  (+ a b))

Why? A docstring is the only documentation most functions will ever have, and the tools that show it — `C-h f`, `apropos`, `(help add)`, the Guile manual — render it in a particular way. A third-person opening reads as a description of the function rather than an instruction to the reader; an argument that is never mentioned is an argument the reader has to infer.

`when` and `unless` say it once

(if (ready?) (go))              ; => (when (ready?) (go))
(if (not (ready?)) (wait))      ; => (unless (ready?) (wait))
(when (not (ready?)) (wait))    ; => (unless (ready?) (wait))

Why? An `if` with one branch is a `when`. An `if` whose test is negated asks the reader to perform a negation while reading, and reading code should not require arithmetic. Both rewrites are purely syntactic: the same test is evaluated and the same forms run. The checks are SIFT012 (`if-without-else`), SIFT033 (`negated-if`), SIFT013 and SIFT014.

Names carry the type

A Lisp has no type declarations to read, so the name is most of what a reader knows: `positive?` is a boolean, `positive` is a number, `*port*` is special, `+pi+` is a constant. Four rules keep the three dialects' conventions apart:

  • SIFT040 `naming-convention`: a definition name with an underscore (`readfile`) or camelCase (`readFile`) is not a Lisp name. The rule looks at definitions only, because a variable bound to somebody else's function is not the linter's to rename.
  • SIFT041 `predicate-name`: a procedure whose last body form is a comparison or another predicate returns a boolean, so its name should end in `?` in Scheme and Common Lisp, and in `-p` (or `?`) in Emacs Lisp. Only the last form counts, because that is the value the procedure returns.
  • SIFT042 `special-variable-name`: Common Lisp earmuffs its special variables (`*port*`) and plus-quotes its constants (`+pi+`); Emacs Lisp does neither, so `*port*` in an Emacs file is a habit from the other dialect.
  • None of them has a fix. Renaming a definition changes every call site in every file, and a formatter that renames one of them has broken the program.

A long expression is a `let` waiting to happen

;; SIFT031 suggests binding the repeated part
(define (f x)
  (list (car (cdr (assq 'a (cdr x))))
        (car (cdr (assq 'b (cdr x))))))

(define (f x)
  (let ((rest (cdr x)))
    (list (car (cdr (assq 'a rest)))
          (car (cdr (assq 'b rest))))))

Why? `let` is how Lisp names an intermediate result, and a name is how a reader stops re-deriving it. Deep nesting (more than four levels) or a very long body form (more than twelve elements) is the signal that the expression wants a step. `let*` is the right form when a later binding refers to an earlier one; `let` when the bindings are independent — and a binding that does not refer to itself belongs in a `let`, which is what SIFT015 says about a `letrec` with one binding.

The check has no fix: choosing the name and the split is the author's work, and a formatter that guesses names is a formatter that writes code.

Keyword arguments past five

(make-window a b c d e f g)                       ; SIFT032
(make-window x y :width 10 :height 20 :title "s") ; says what it means

Why? A positional argument is only readable when the reader remembers the argument list. Five is where that stops being true in practice: at the call site, the sixth `#t` says nothing, and a keyword says everything. `sift` reports the call, not the definition, because the callee's shape is the author's to decide; the rule skips special forms and the calls that are meant to be variadic (`list`, `format`, `+`), and the limit is configuration (`max-positional`).

Packages are named, and never reached into

In Common Lisp, an exported symbol is written with its package prefix (`app:run`), and a double colon (`other::internal`) is for debugging, not production. SIFT025 and SIFT026 say so, because a file that uses `other::internal` is a file that breaks when `other` is reorganised, and a file that uses `run` unqualified depends on whatever `*package*` happens to be at read time.

The rule catalogue

Every rule has a name (what you type) and a code (what an editor shows and what a bug report quotes). The code is stable: it is never reused, and a new rule takes the next number.

The complete, generated list — every rule with its code, dialects, severity, example and fix — is in rules.org, written by maak docs from the rule records themselves, so it cannot name a rule that does not exist and the test suite fails when it falls behind. What follows is the reasoning: the rules grouped by dialect, with the case for each one.

Why these are cross-dialect: they are about the text (whitespace, length, delimiters) or about a form all three dialects share (`if`, `when`, `progn`, `let`). Everything about a specific dialect's bookkeeping is in that dialect's section.

Why SIFT001 and SIFT002 matter: trailing whitespace is invisible and shows up in every diff; a tab renders at a different width in every editor, so indentation that uses one is not indentation the next reader will see.

Why SIFT004 has no fix: putting a `)` where sift thinks it belongs is a guess about what the program means. sift reports the opening delimiter and stops.

Why SIFT006 exists: `(define (f) (progn (a) (b)))` says "a progn" twice — the body of a definition is already a sequence.

SIFT013 when-without-body warning `when` with no body

SIFT011: Scheme allows definitions at the head of a body, but a `define` in the middle of an expression defines in the wrong scope — it is almost always a `let` that got written as a `define`.

SIFT013/SIFT014: `(when x)` does nothing at all. Either the body was lost in an edit, or the form should not be there.

SIFT015: `letrec` promises that the bindings may refer to each other. With one binding that does not, it promises something untrue, and the reader looks for the recursion that is not there.

SIFT016: `` `(1 ,2) `` evaluates to the same list as `` `(1 2) ``. The unquote is a leftover from a version where the value was computed.

SIFT035: Guile renders docstrings as Texinfo. An argument written `x` is plain text; `@var{x}` is typeset as a metavariable in `C-h f` and in the manual, which is what a parameter is.

SIFT036: see Square brackets for `cond` clauses.

These are the Emacs Lisp Reference Manual's own requirements, taken one at a time so a project can adopt them one at a time. SIFT020 is the one with consequences beyond style: a file without the header is loaded with dynamic binding, which changes what a closure captures.

Common Lisp rules

Code Rule Severity What it says
SIFT025 package-prefix warning an exported symbol is used without its package prefix
SIFT026 double-colon warning `package::symbol` reaches into another package's internals
SIFT027 dangling-paren warning a closing parenthesis is on its own line

SIFT027 is the Common Lisp half of the community-style decision: the Google Common Lisp style guide, and every Lisp I know, keeps the closer on the last line.

SIFT029 is the only rule that is silent by default: LOOP accepts both `for` and `:for`, communities differ, and a rule that fires on half the world's `loop` forms is a rule that gets switched off. Set `loop-keywords: literal` (or `symbolic`) to enforce one.

SIFT030: `identity` in value position is a no-op, and `(funcall #'foo x)` is `(foo x)`.

Three rules about shape

SIFT008 (`empty-form`) exists because `()` reads as "the empty list" and evaluates as an error in Scheme: it is data that needs a quote, and the place it happens is almost always a forgotten `'()`. The rule is careful not to fire on a parameter list, a binding list or quoted data — where `()` is exactly right — and it says nothing at all in Emacs Lisp and Common Lisp, where `()` is `nil`.

SIFT037 (`duplicate-binding`) catches `(let ((x 1) (x 2)) …)`. In `let*` it is legal and still almost always a mistake: the first binding is dead, and a reader cannot see that without comparing names.

SIFT009 (`duplicate-keyword`) catches `(make-window :width 10 :width 20)`: one of the two values is being discarded, and nothing in the code says which.

SIFT038 (`docstring-before-interactive`) is the Emacs Lisp rule that is easiest to get wrong by accident: Emacs reads a docstring from the first form of the body, so a string after `(interactive)` documents nothing and `C-h f` shows nothing, while the file looks documented.

What sift will not do

  • It will not reflow. Long lines are reported (SIFT003), not broken.
  • It will not guess. An unbalanced file is refused, with the position of the opening delimiter, unless `–force` says "format what you can read".
  • It will not fix without `–fix`, and it will not apply a fix that makes the file parse worse. A fix that would introduce a new parse error is discarded along with every other fix of that run.
  • It will not rewrite an expression. Every fix is either a delimiter, a piece of whitespace, a docstring insertion, or a syntactic equivalence (`if (not x)` → `unless x`). Names are never invented.
  • It will not touch a datum comment, a `#.` form or a `#<…>` object. Those are copied verbatim; formatting inside them would be a guess about code the reader was told not to read.

How to disagree

  1. Turn a rule off for a line or a form: 

    ;; sift:disable-next-line keyword-arguments
(make-window a b c d e f g)

;; sift:disable wrap-in-let
(define (f x)
  ...)
;; sift:enable wrap-in-let
  2. Run fewer rules: `–checker`, `–exclude-checker`, or a `checkers:` list in `sift.yaml`.
  3. Change a threshold: `line-length`, `max-depth`, `max-elements`, `max-positional`, `indent`, `brackets`, `loop-keywords`.
  4. Ask why: `sift explain RULE` prints the rule's code, description, dialects, severity, a failing example and the fix it expects; and `M-x sift-explain-at-point` in Emacs does it from the line you are on.

The style in one page

;;; Commentary:
;;
;; Two columns, one blank line, closers that trail.
;;; Code:

(define (classify n)
  "Return a symbol describing @var{n}.

The name says more than the number does at the call site."
  (cond [(< n 0) 'negative]
        [(= n 0) 'zero]
        [else 'positive]))

(define (report n)
  (let ((kind (classify n)))   ; the name is the documentation
    (when (symbol? kind)       ; one branch: when, not if
      (display kind))))

Everything above is what `sift format` produces from the same code written without care, and everything that is not whitespace was already the author's.

#+title: sift as a language server
#+author: Josep Bigorra

#+options: toc:2 num:nil
#+language: en

The requests `sift lsp` answers, request by request, and the requests it
refuses.  A feature that is absent is a line here, rather than a guess made
from the editor's side.  The moving parts are drawn in
[[file:diagrams.md][doc/diagrams.md]]: navigation, the two diagnostic passes, the standard
library and its downloads, import organization and file renames.

* What the language server answers
:PROPERTIES:
:CUSTOM_ID: lsp-coverage
:END:

~sift lsp~ answers what sift can answer truthfully and refuses the remainder
with the protocol's own "method not found" error, since a server that answered
every request an editor can make would be misrepresenting half of them.  The
table below is exhaustive, so a feature absent from it is absent from the
server.

| Request                                              | Status  | What sift does                                                                    |
|------------------------------------------------------+---------+-----------------------------------------------------------------------------------|
| ~initialize~, ~shutdown~, ~exit~                     | yes     | the capabilities below, and the exit status the protocol asks for                 |
| ~textDocument/didOpen~, ~didChange~, ~didClose~       | yes     | full synchronisation: the buffer is linted on every change                        |
| ~textDocument/didSave~                               | yes     | the file is read again for the index, every open buffer is checked again, and the dialect's compiler is asked for its second opinion |
| ~workspace/didChangeWatchedFiles~                    | yes     | a file changed outside the editor is re-read, or forgotten if it went away; the open buffers are checked again |
| ~workspace/didChangeConfiguration~                   | yes     | the settings are read again -- the editor's whole object, sift.yaml, the user's, the command line -- and every open buffer is checked against them |
| ~workspace/willRenameFiles~                          | yes     | the module a Scheme file names, or the feature an Emacs Lisp file provides, follows the new file name; the project's imports of it are updated; a Common Lisp file has no name to change |
| ~workspace/didRenameFiles~                           | yes     | the renamed file is re-read for the index, or forgotten if it left the project, and the open buffers are checked again |
| ~textDocument/publishDiagnostics~                    | yes     | every finding, with its code, its severity and the rule's page; the compiler's findings follow as a second report for the same version |
| ~textDocument/codeAction~                            | yes     | the rule's own fix as ~quickfix~; fix everything as ~source.fixAll.sift~; format this definition as ~refactor.rewrite~; extract an expression to a ~let~ binding or to a procedure, or a lambda to a procedure of its own, as ~refactor.extract~; replace a call with the body it calls as ~refactor.inline~; optimize imports (remove the unused ones) as ~source.optimizeImports.sift~; sort imports as ~source.sortImports.sift~; both as the standard ~source.organizeImports~; honours ~context.only~ |
| ~codeAction/resolve~                                 | no      | an action is computed from the buffer the editor sent, so there is nothing to fill in later |
| ~textDocument/formatting~                            | yes     | one edit for the buffer, or a message saying why it refuses                       |
| ~textDocument/hover~                                 | yes     | a symbol's definition and docstring, or what the implementation says about a builtin; a finding's rule otherwise |
| ~textDocument/definition~                            | yes     | Scheme, Racket, Emacs Lisp and Common Lisp: scope first, then the file, then the project, then the standard library |
| ~textDocument/references~                            | yes     | every mention in the project, by name, within one dialect; a binding's mentions are the ones inside the form that binds it |
| ~textDocument/documentHighlight~                     | yes     | the mentions in this buffer, the declaration marked apart from the uses           |
| ~textDocument/documentSymbol~                        | yes     | the outline, a definition nested inside the one that holds it                     |
| ~workspace/symbol~                                   | yes     | that outline searched by substring                                                |
| ~textDocument/completion~                            | yes     | the names the buffer, the project and the standard library define, the last of them only for what is being typed; no snippets, no arithmetic |
| ~textDocument/inlayHint~                             | yes     | a parameter's name beside each positional argument of a call sift can resolve, and the type a literal states when ~inlay-hints: [parameters, types]~ asks for it |
| ~textDocument/prepareRename~, ~rename~               | yes     | a binding inside the form that binds it, a file-level definition by name across the project; a name that is not a symbol is refused |
| ~window/showMessage~ (server to client)              | yes     | used to say why formatting or a rename was refused                                |
| ~window/logMessage~ (server to client)              | yes     | what the server did: the root it serves, the dialect of each buffer, the findings a report carries, every re-read |
| ~window/workDoneProgress/create~, ~$/progress~ (server to client) | yes | indexing the standard library and its downloaded sources, when the client advertises ~window.workDoneProgress~; otherwise the same lines are log messages |
| ~$/cancelRequest~, ~$/setTrace~                      | ignored | a request is answered before a cancel could reach it; nothing is traced           |
| ~textDocument/signatureHelp~                         | yes     | the formal list -- keywords and optionals as they are written -- the argument being written, and the docstring; a procedure that takes nothing gets ~(name)~ |
| ~textDocument/declaration~, ~typeDefinition~, ~implementation~ | no | sift models no types and expands no macro, so there is no hierarchy to answer |
| ~textDocument/callHierarchy~, ~typeHierarchy~        | no      | a call is a form whose head is a symbol, and nothing more is known                |
| ~textDocument/semanticTokens~                        | no      | highlighting is the editor's business                                             |
| ~codeLens~                                           | no      | a lens would have to guess at what it is for                                      |
| ~textDocument/foldingRange~                          | no      | the formatter has no opinion about what to fold                                   |
| ~textDocument/rangeFormatting~, ~onTypeFormatting~   | no      | sift formats a whole buffer or nothing                                            |
| ~textDocument/diagnostic~ (pull)                     | no      | findings are pushed after every change                                            |
| ~workspace/didChangeWorkspaceFolders~                | no      | the root is read once, at ~initialize~                                            |

Two limitations belong beside the table rather than in an issue tracker.  A
reference is matched *by name, within one dialect*: sift expands no macro,
follows no ~define-module~ import and reads no ~defpackage~, so a name
introduced by a macro is invisible to ~references~ and to ~rename~.  The
project is read once per session, on the first request that requires it;
afterwards it is refreshed only when the client says so -- a ~didSave~, a file
changed on disk, a configuration edited and saved -- which is why the server
requests ~openClose~, a full change and ~save~ in its synchronisation options
rather than the bare change kind ~1~.  An editor that sends none of these
leaves the server answering from what it read when the session started.

The code actions are the five operations sift can perform without being told
what anything should be called: fix the finding under the cursor (~quickfix~);
bind the expression under the cursor to a name around the form that held it,
move it into a procedure beside the definition it came from, give a lambda a
name of its own and move that to the top level, or write a `define` whose whole
value is a lambda as the procedure it is, under the definition's own name (all
~refactor.extract~); 
replace a call with the body it calls (~refactor.inline~); and fix or reformat
the form the cursor is inside (~source.fixAll.sift~, ~refactor.rewrite~, the
latter offered only for a top-level form, because the formatter indents from
column zero and a fragment would land at the margin).

The two import operations are the ones an editor is most likely to run on
save.  ~sift: optimize imports~ applies the fix ~unused-import~ already
computes; ~sift: sort imports~ puts the specifications of every import form in
alphabetical order by library name -- the specs of an ~(import ...)~ and the
~#:use-module~ clauses of a ~define-module~, which is the shape most Guile and
Guix code uses.  The standard ~source.organizeImports~
action does whichever of the two the project has enabled -- both are on by
default, and ~optimize-imports~ and ~sort-imports~ in ~sift.yaml~ turn either
off.  Sorting permutes the specifications in place, so a form written on one
line stays on one line and a form written one spec per line keeps its
indentation.  `sift fix` asks the same two questions of a file, so the command
line and the editor tidy imports the same way.

An expression written inside a binding list -- the `(compute 1)' of
`(let ((x (compute 1))) x)' -- is bound around the `let`, and not around the
binding list it sits in, because the latter would write
`(let ((v (compute 1))) ((x v)))', which is not a program.  An extraction
derives its name from the expression -- `(compute-area w h)' becomes
~compute-area~ -- and a name the file already uses becomes ~compute-area-2~
rather than shadowing it.  An extraction that moves a lambda
writes its definition before the form in which the lambda occurred, and
inlining is offered only where it requires no guessing: a definition in this
buffer, with a single expression in its body, plain positional parameters, and
none of them rebound inside the body -- otherwise no action is offered in
place of an approximation.  A rename is a refactor as well, but it requires a
new name, so it is the protocol's own ~textDocument/rename~ rather than an
action that would have to invent one -- the same line ~sift fix~ draws
everywhere else.

* While the project is being read
:PROPERTIES:
:CUSTOM_ID: lsp-index
:END:

The project is read in a thread of its own, from the moment ~initialize~ names
a root, and no request waits for it.  What a jump or a reference search sees
is the snapshot the indexer last published: a project of two thousand files is
published in batches of sixty-four, so the first answer arrives after the
first batch rather than after the last file, and every later batch replaces the
snapshot whole rather than editing it under a reader.

A client that advertises ~experimental~ in its capabilities is told where the
index is, as a notification:

#+begin_src json
{"jsonrpc": "2.0", "method": "sift/indexStatus",
 "params": {"state": "indexing", "done": 64, "total": 2000}}
#+end_src

The states are ~uninitialized~ (no root yet), ~scanning~ (the tree is being
listed), ~indexing~ (~done~ of ~total~ files are read) and ~ready~.  The
notification is sent on every state change and on every published batch, and
it is also what a test waits for instead of guessing at a sleep.  A client that
does not advertise ~experimental~ is not sent it, and loses nothing else.

Until the snapshot has a file, a jump to a name defined there is answered with
an empty result rather than a wait, and the server says in the editor's log
that the index is still being read.  Both navigations are bounded: a
definition is answered within one hundred milliseconds, a reference search
within two hundred, and $/cancelRequest is checked between the steps of either
one.  The measurement behind that bound is in ~benchmarks/sift.scm~: a jump
against two thousand indexed names costs about 0.02 ms, whether the index is
complete or still being read.

A lint is a job on a queue drained by its own worker, so a keystroke does not
compute a finding in the loop that reads messages: the request that follows it
is answered while the buffer is being checked.  A report is about the text it
was computed from, so a job that finishes after the buffer changed is dropped
instead of drawing old findings over new text, and a closed buffer is not
reported about at all.

* Where the standard library comes from
:PROPERTIES:
:CUSTOM_ID: lsp-stdlib
:END:

A name a project does not define is usually a name the dialect does, and a
server that answered "not here" to every one of them would be answering about
one name in three.  So the library an implementation ships with itself is
indexed as well, from its two halves.

The first half is *source*.  Guile's own modules are the directories
~%load-path~ names -- the ~ice-9~, ~srfi~, ~scheme~ and ~rnrs~ files of the
installation, the user's own site directory, plus whatever a profile has added
to them.  Emacs Lisp's are the files on ~load-path~, and the package trees
under ~package-user-dir~ (~~/.emacs.d/elpa~ by default) and the system's
~site-lisp~, because a batch Emacs that ran no init file has neither on
~load-path~.  Common Lisp has no such variable, so sift looks where ASDF does:
~common-lisp/source~ under the usual data directories, the SBCL contrib, and a
Quicklisp or Roswell tree in the home directory.  Those files are read, parsed
and asked the same question a project's files are, so `(srfi srfi-1)'s `fold`
lands on the `define` that defines it, a third-party package lands on the
source that package installed, and the hover is the hover of any other
definition.

Racket's are the ~collects~ and ~pkgs~ directories of the installation the
~racket~ on the path belongs to, the version trees a user-scope package went
into under the data directory, and whatever ~PLTCOLLECTS~ names -- the variable
Racket itself reads.  Racket is the one dialect whose index is all source and
no second half: there is no Racket program shipped to describe ~racket/base~,
because the files that define it are already there.  What that leaves out is
the name only the compiled ~#%kernel~ defines, which is answered as no file
defining it rather than as a guess.

A source may be *compressed*: most Emacs installations ship ~foo.el.gz~, and
a project that vendors one has the same shape.  It is read through ~gzip~ as
the editor reads it, so the answer is the definition in the source rather than
a name the index never saw.

The second half is what an implementation *knows about itself*.  `car` is
compiled into libguile and no file in the installation says where; `dolist` is
a macro the Emacs binary carries; `loop` is a symbol in the `COMMON-LISP`
package and its documentation is in SBCL.  Each implementation is therefore
asked once, in a single process, to write down every name it documents, with
the argument list and the prose it carries.  That file becomes an answer too:
a jump to `car` lands on the entry that describes it, and the hover shows the
argument list and the sentence, or says plainly that this installation carries
no documentation for the name.  The file opens with a line saying what it is,
so a reader who arrives there by jumping was told why they are there.

A library that is not installed is not guessed at.  The answer is the smaller
one -- the project, the buffers, and the rule under the cursor -- unless the
project names a source URL and turns ~download-sources~ on: then the archive is
fetched with ~curl~ into ~$XDG_CACHE_HOME/sift/sources/~ (or the platform's
cache directory), checked before it is unpacked with ~tar~, and the tree
becomes one more root.  A source already in the cache is not fetched again, and
a failed fetch is one source missing rather than a library that cannot be read.
Three things decide what is read.

- the *setting*: ~stdlib: true~ (the default) reads what this machine has
  installed; ~stdlib: false~ reads none of it; and a list of directories and
  source URLs reads those instead.  A URL is fetched only when
  ~download-sources: true~ is set as well, so a project file cannot make sift
  reach the network on its own.  [[file:configuration.org::#configuration][configuration.org]] has the shape.
- the *cache*: the index is written under ~$XDG_CACHE_HOME/sift/stdlib/~ --
  ~<dialect>.json~ for the names, ~<dialect>-builtins.txt~ for the
  documentation -- and read from there in later sessions.  It is keyed on the
  implementation's own binary, so a Guile that was upgraded is read again
  rather than answered about from an index of the old one; deleting the
  directory is always safe.  Downloaded archives and their trees live beside it
  under ~sources/~.
- the *clock*: the first read of a library takes a second or two for a small
  one and a good deal longer for a machine with a thousand installed packages,
  so it happens in a thread of its own when the client says it is ready.  A
  name in the library answers nothing until that read has finished -- the
  server says what it found, and how much, in its log -- and answers from then
  on.
- the *report*: a client that advertises ~window.workDoneProgress~ gets a
  progress token, a begin, one report per source and per library, and an end;
  a client without it gets the same lines through ~window/logMessage~.  A
  source that was downloaded, a source that came from the cache and a library
  that was indexed are all said out loud, so "still working" and "nothing to
  read" do not look alike.

Three limitations are worth knowing, and all three are the same promise the
rest of sift makes: it reads the text there is.  A name an implementation
binds without documenting -- Guile's `if`, in an installation whose docstrings
were not built -- has an entry with its kind and its argument list and no
prose, because there is none to read.  A name is matched, not *resolved*: sift
never says which library exports a name, and never follows an import.  And a
definition in the project always wins, because a definition in the project is
the one the reader is asking about.

* The compiler's second opinion
:PROPERTIES:
:CUSTOM_ID: lsp-compiler
:END:

The reader knows the shape of a form; the compiler knows the names inside it.
When a buffer is opened or saved, sift asks the dialect's own compiler --
~guild compile~, Emacs's byte compiler, ~sbcl~ with ~compile-file~ -- and
publishes what it says as a second report for the same version.  The fast
report arrives first; the compiler's findings arrive when the process exits,
with ~source~ set to ~guild~, ~emacs~ or ~sbcl~.  An unbound variable, a call
with the wrong number of arguments, a free variable in a byte-compiled file and
the type warnings SBCL can state from a declaration are all reported as the
compiler states them.

The text is written to a temporary file, compiled there and removed: nothing is
written into the project, and an unsaved buffer is compiled as it is.  The
compiler runs in a thread, its output is bounded, and a text it has already
compiled is not compiled again.  ~compiler-diagnostics: false~ turns the
second opinion off.

Two things are worth knowing.  A compiler expands macros, so compiling a file
runs the code those macros contain; this is the project's own compiler and the
project's own code, and the setting is the place to say no.  And there is no
hard timeout: a compiler that hangs holds its thread until the session ends.
A position is exact when the compiler prints one; SBCL reports the form it
echoed rather than a line, so the form is searched for in the source, and a
condition that names neither lands on the first character.

* Renaming a file
:PROPERTIES:
:CUSTOM_ID: lsp-rename-file
:END:

The protocol asks whether a file rename should be accompanied by edits
(~workspace/willRenameFiles~), and the answer depends on what a module is in
the dialect.

- *Scheme*: a file that declares a library with ~define-module~,
  ~define-library~ or ~library~ keeps that name in step.  The last segment
  follows the new file name -- ~(app util)~ in ~util.scm~ becomes
  ~(app helpers)~ when the file becomes ~helpers.scm~ -- and every import of
  ~(app util)~ in the project is updated.  The rule applies only when the old
  module's last segment is the old file name; a module name that has nothing to
  do with the file is left alone rather than guessed at.
- *Emacs Lisp*: the feature the file ~provide~s becomes the new file name, and
  every ~require~ of the old feature in the project asks for the new one.  A
  file with no ~provide~ has only its ~require~s updated.
- *Common Lisp*: a package is not a file.  A file rename changes no package,
  no system and no ~in-package~, so the answer is no edit rather than a guess.

`workspace/didRenameFiles` is the other half: the old path leaves the index,
the new path is read, and every open buffer is checked again, because a
finding can name either.

What `sift lsp` answers, request by request, and what it refuses.
A missing feature is a line here rather than a guess made from the editor's
side.

* What the language server answers
:PROPERTIES:
:CUSTOM_ID: lsp-coverage
:END:

~sift lsp~ answers what sift can answer truthfully and refuses the rest with
the protocol's own "method not found", because a server that answered every
request an editor can make would be lying about half of them.  This table is
the whole of it, so a missing feature is a line here rather than a guess made
from the editor's side.

| Request                                              | Status  | What sift does                                                                    |
|------------------------------------------------------+---------+-----------------------------------------------------------------------------------|
| ~initialize~, ~shutdown~, ~exit~                     | yes     | the capabilities below, and the exit status the protocol asks for                 |
| ~textDocument/didOpen~, ~didChange~, ~didClose~       | yes     | full synchronisation: the buffer is linted on every change                        |
| ~textDocument/didSave~                               | yes     | the file is read again for the index, and every open buffer is checked against it |
| ~workspace/didChangeWatchedFiles~                    | yes     | a file changed outside the editor is re-read, or forgotten if it went away; the open buffers are checked again |
| ~workspace/didChangeConfiguration~                   | yes     | the settings are read again -- sift.yaml, the user's, the command line -- and every open buffer is checked against them |
| ~textDocument/publishDiagnostics~                    | yes     | every finding, with its code, its severity and the rule's page                    |
| ~textDocument/codeAction~                            | yes     | the rule's own fix as ~quickfix~; fix everything as ~source.fixAll.sift~; format this definition as ~refactor.rewrite~; extract an expression to a ~let~ binding or to a procedure, or a lambda to a procedure of its own, as ~refactor.extract~; replace a call with the body it calls as ~refactor.inline~; honours ~context.only~ |
| ~codeAction/resolve~                                 | no      | an action is computed from the buffer the editor sent, so there is nothing to fill in later |
| ~textDocument/formatting~                            | yes     | one edit for the buffer, or a message saying why it refuses                       |
| ~textDocument/hover~                                 | yes     | a symbol's definition and docstring; a finding's rule otherwise                   |
| ~textDocument/definition~                            | yes     | Scheme, Emacs Lisp and Common Lisp: scope first, then the file, then the project   |
| ~textDocument/references~                            | yes     | every mention in the project, by name, within one dialect                         |
| ~textDocument/documentHighlight~                     | yes     | the mentions in this buffer, the declaration marked apart from the uses           |
| ~textDocument/documentSymbol~                        | yes     | the outline, a definition nested inside the one that holds it                     |
| ~workspace/symbol~                                   | yes     | that outline searched by substring                                                |
| ~textDocument/completion~                            | yes     | the names the buffer and the project define, ranked by what is being typed; no snippets, no arithmetic |
| ~textDocument/inlayHint~                             | yes     | a parameter's name beside each positional argument of a call sift can resolve, and the type a literal states when ~inlay-hints: [parameters, types]~ asks for it |
| ~textDocument/prepareRename~, ~rename~               | yes     | by name across the project; a name that is not a symbol is refused                |
| ~window/showMessage~ (server to client)              | yes     | used to say why formatting or a rename was refused                                |
| ~window/logMessage~ (server to client)              | yes     | what the server did: the root it serves, the dialect of each buffer, the findings a report carries, every re-read |
| ~$/cancelRequest~, ~$/setTrace~                      | ignored | a request is answered before a cancel could reach it; nothing is traced           |
| ~textDocument/signatureHelp~                         | yes     | the formal list -- keywords and optionals as they are written -- the argument being written, and the docstring; a procedure that takes nothing gets ~(name)~ |
| ~textDocument/declaration~, ~typeDefinition~, ~implementation~ | no | there are no types here, and no macro is expanded                        |
| ~textDocument/callHierarchy~, ~typeHierarchy~        | no      | a call is a form whose head is a symbol, and nothing more is known                |
| ~textDocument/semanticTokens~                        | no      | highlighting is the editor's business                                             |
| ~codeLens~                                           | no      | a lens would have to guess at what it is for                                      |
| ~textDocument/foldingRange~                          | no      | the formatter has no opinion about what to fold                                   |
| ~textDocument/rangeFormatting~, ~onTypeFormatting~   | no      | sift formats a whole buffer or nothing                                            |
| ~textDocument/diagnostic~ (pull)                     | no      | findings are pushed after every change                                            |
| ~workspace/didChangeWorkspaceFolders~                | no      | the root is read once, at ~initialize~                                            |

Two limits belong next to the table rather than in an issue.  A reference is
matched *by name, within one dialect*: sift expands no macro, follows no
~define-module~ import and reads no ~defpackage~, so a name a macro invents is
invisible to ~references~ and to ~rename~.  And the project is read once per
session, on the first request that needs it: what refreshes it afterwards is
the client saying so -- a ~didSave~, a file changed on disk, a configuration
edited and saved -- which is why the server asks for ~openClose~, a full change
and ~save~ in its synchronisation options instead of the bare change kind ~1~.
An editor that sends none of those is an editor sift can only answer from what
it read when the session started.

The code actions are the five things sift can do without being told what to
call anything: fix the finding under the cursor (~quickfix~); bind the
expression under the cursor to a name around the form that held it, move it
into a procedure beside the definition it came from, or give a lambda a name of
its own and move that to the top level (all ~refactor.extract~); replace a call
with the body it calls (~refactor.inline~); and fix or reformat what the cursor
is inside (~source.fixAll.sift~, ~refactor.rewrite~, the latter offered only
for a top-level form because the formatter indents from column zero and a
fragment would land at the margin).
An extraction names what it extracts from the expression -- `(compute-area w
h)' becomes ~compute-area~ -- and a name the file already uses becomes
~compute-area-2~ rather than shadowing it.  An extraction that moves a lambda
writes its definition before the form the lambda was in, and inlining is only
offered where it needs no guessing: a definition in this buffer with one
expression in its body, plain positional parameters, and none of them rebound
inside the body -- otherwise there is no action rather than an approximation.
A rename is a refactor too, but it needs a new name, so it is the protocol's
own ~textDocument/rename~ rather than an action that would have to invent one
-- which is the same line ~sift fix~ draws everywhere else.

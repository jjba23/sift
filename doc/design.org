Six propositions the code is measured against, and the decisions that follow
from them as consequences.

* The propositions
:PROPERTIES:
:CUSTOM_ID: beliefs
:END:

The decisions in the next chapter derive from six propositions.  They are
stated apart because they are the standard a rule is measured against when one
is added and it has to be settled what that rule may do.

1. *A source file is a datum, not a string.*  A comment that keeps its column,
   a fix that replaces one range, a diff whose hunks are the change: all three
   follow from reading a Lisp file as a tree of forms carrying source
   positions.  A formatter that treats a buffer as lines of text can preserve
   positions or it can be fast; the two are hard to hold at once.

2. *Formatting is a fixed point, and the property is tested.*  A file returns
   byte for byte, a fix that cannot be verified is discarded rather than
   guessed at, and the test suite asserts idempotence over every fixture: the
   property holds by measurement, not by declaration.

3. *The author owns the program; the tool owns the layout.*  sift re-indents,
   re-spaces, re-levels comments and re-brackets a ~cond~ clause.  It does not
   rename, does not reorder, does not inline a procedure written by hand, and
   does not introduce a delimiter.  The rules whose correctness would require
   the author's intent — ~wrap-in-let~, ~line-length~, the naming rules —
   report, and stop there.

4. *A dialect is a language, not a variant.*  Common Lisp is not Scheme with
   longer names: its package prefixes, its ~LOOP~, its docstrings and its
   dangling parentheses are read as itself, and the same file is not
   reformatted as Scheme because it was opened in the wrong mode.  A formatter
   that infers the dialect will, one day, rewrite Common Lisp as Scheme.

5. *A request is answered only where the answer can be justified.*  The
   language server answers the requests in
   [[file:language-server.org][the language server page]] and answers the others
   with "method not found".
   [[file:../README.org::#web][The browser build]] has no project to read, so
   the two rules that need one say nothing at all.  A refusal is a feature
   when the only alternative is a plausible lie.

6. *Every utterance of the program is available as data.*  A finding is the
   same finding in five output formats and over LSP, a rule is a record before
   it is a document, and every integration in this repository is a thin wrapper
   over the program rather than a second implementation of it.  The same
   argument makes [[file:../README.org::#web][the browser]] a compile of the
   same modules and not a JavaScript rewrite: two implementations of a style
   are two styles.

None of this is a claim to cleverness.  A formatter is useful in proportion to
how predictable it is, and every rule here that looks clever is a rule whose
plain version would have lost something the reader needed.

* The decisions that follow
:PROPERTIES:
:CUSTOM_ID: decisions
:END:

** A reader of its own
:PROPERTIES:
:CUSTOM_ID: own-reader
:END:

~read~ discards comments, keeps no source positions, and cannot represent a
block comment, a datum comment or a reader prefix as a node: the abstract
syntax it returns has no place to put them.  Each property claimed here —
round trip, idempotence, a fix that replaces exactly one range, a comment that
stays on its line — requires those nodes.  The reader is also deliberately
permissive: a file with one broken form still gets a tree, because a linter
that reports nothing about a file it could not fully parse fails exactly when
it is needed.  The language server rests on the same property: a buffer being
typed is a buffer with a broken tail, and it still receives the findings for
everything before the break.

** One traversal, and the answers kept
:PROPERTIES:
:CUSTOM_ID: one-walk
:END:

Three questions dominated the cost of a lint, and each was answered by walking
something a second time.  Whether a node is code or data -- it is data inside a
quote, inside a vector literal, in the datum of a ~case~ clause, in a parameter
list -- was decided by walking *up* the ancestors for every node of every
checker's walk, which is one walk per node per enclosing level.  What a form is
called, and which of its children carry a datum, was recomputed by walking its
children every time any checker asked.  And where the lines of a
file begin was worked out afresh for every finding, by consing the list of
every line in the file.

Each is now computed once and either carried or kept: the data-or-code answer
is carried *down* by the walk that asks it, the two questions about a node are
answered on their first asking and kept in a cache slot on the node (a node is
immutable, so the cache cannot go stale), and the line starts of a text are
kept until a different text is asked about.  Together they took a lint of this
repository from twenty-five seconds to under one, and the allocation per lint
from a gigabyte and a half to a hundred and forty megabytes.  The same figure
governs [[file:configuration.org::#parallel][the parallel run]]: Guile's garbage
collector stops every thread, so a lint that allocates less is a lint that
parallelises better.

** Layout, not pretty-printing
:PROPERTIES:
:CUSTOM_ID: fuzzy
:END:

A pretty-printer decides the line breaks again from scratch, which produces
diffs that are not about the change being made.  sift moves whitespace and
delimiter characters and leaves the chosen line structure intact.

** No fixing without ~--fix~
:PROPERTIES:
:CUSTOM_ID: no-fix-without
:END:

A linter that fixes by default cannot be used to check anything.  Hence ~lint~
reports, ~lint --fix~ fixes, ~ci~ refuses to do either.

** ~check~ and ~ci~ are separate commands
:PROPERTIES:
:CUSTOM_ID: check-ci
:END:

~format~ prints, ~--write~ writes, ~check~ answers with the status alone, and
~ci~ asks the formatting question and the lint question in one go.  These are
the shapes a hook and a pipeline require, and giving them names keeps ~format~
safe to pipe.

** A small YAML reader
:PROPERTIES:
:CUSTOM_ID: yaml
:END:

The configuration needs block mappings, sequences, scalars, inline lists,
comments and positions.  A full YAML implementation is more surface than sift
itself; a data-only subset that refuses what it does not understand, with a
line and a column, is a smaller surface than the faults a general one brings.
The same argument, later, produced
[[file:../src/sift/json.scm][src/sift/json.scm]]: the language server
needs JSON, and sift should not need a package installed before its own server
starts.

** Codes that never move
:PROPERTIES:
:CUSTOM_ID: codes
:END:

A rule's name is the token typed to select it; its code (SIFT012) is what an
editor attaches to a diagnostic and what a bug report quotes.  Codes are
assigned by hand, never reused, and the catalogue is generated from them, so a
log from an earlier release still denotes what it denoted.
